## 3.1. Три вопроса, на которые отвечает event loop

Вернёмся к официанту, который не стоит без дела. Чтобы так работать, ему нужно уметь три вещи:

1. **Помнить, какие заказы у него сейчас «в работе»** — и что именно по каждому заказу ещё осталось сделать.
2. **Понимать, чего каждый заказ ждёт**: пока не приготовится еда, пока гость выберет десерт, пока придёт оплата.
3. **Переключаться на тот заказ, который прямо сейчас готов к следующему шагу**, а если готовых нет — спокойно ждать, не тратя силы.

Event loop (цикл событий) — это в точности такой «мозг официанта». В программе его роль такая:

- «заказ» — это **задача** (task): функция, которая умеет приостанавливаться;
- «чего заказ ждёт» — это **событие**: прошло время, пришёл ответ по сети, освободился диск;
- «мозг» — это **бесконечный цикл**, который раз за разом выбирает задачу, готовую двигаться дальше, и даёт ей поработать до следующего ожидания.

Слово «цикл» здесь буквальное: внутри event loop лежит обычный `while`.

## 3.2. Начнём с проблемы: синхронный код в замерах

Сделаем «запрос», который просто ждёт полсекунды (как будто мы сходили в сеть):

```python
import time

def fake_request(name, delay=0.5):
    time.sleep(delay)
    return name
```

`time.sleep(0.5)` — это **блокирующее** ожидание: поток честно засыпает на полсекунды и ничего больше не делает. Выполним три таких «запроса» подряд:

```python
t = time.perf_counter()
for n in ["A", "B", "C"]:
    fake_request(n)
print("sequential: %.2f" % (time.perf_counter() - t))
```

Результат: **1.50 секунды** — три раза по 0.5. Ровно то, что мы обсуждали в модуле 0: пока идёт первый «запрос», второй даже не начался.

## 3.3. Первое решение: потоки

**Поток (thread)** — это отдельная «нить» выполнения внутри одной программы. Операционная система умеет запускать много потоков и переключаться между ними. Три потока — три «официанта».

```python
import threading

t = time.perf_counter()
threads = [threading.Thread(target=fake_request, args=(n,)) for n in ["A", "B", "C"]]
for th in threads: th.start()
for th in threads: th.join()
print("threads: %.2f" % (time.perf_counter() - t))
```

Разбор синтаксиса:

- `threading.Thread(target=..., args=(...))` создаёт поток, который выполнит функцию `target` с аргументами `args`. Сам поток при этом ещё **не запущен**.
- `th.start()` запускает поток: он начинает работать параллельно с остальными.
- `th.join()` говорит главному потоку: «подожди, пока этот поток закончит». Без `join` программа могла бы выйти раньше, чем потоки закончили работу.

Результат: **0.50 секунды**. Все три «запроса» ждали одновременно, и общее время сравнялось с самым долгим из них.

Потоки работают, но у них есть цена и особенность:

- **Цена.** Каждый поток занимает память и требует от операционной системы работы по переключению. Десяток потоков — ерунда, десятки тысяч — уже проблема (мы обсуждали это в модуле 0).
- **Вытесняющая многозадачность.** Переключением потоков управляет операционная система, и она может «выдернуть» поток из работы **в любой момент**, даже посередине строки вроде `count += 1`. Если два потока одновременно меняют одни и те же данные, результат может оказаться непредсказуемым. Поэтому в многопоточном коде приходится защищать общие данные блокировками — это отдельный источник ошибок, которые трудно воспроизвести и отловить.

Запомни это слово: *вытесняющая* — переключение происходит там, где решит система, а не сам код. В event loop всё будет иначе.

## 3.4. GIL: почему потоки не ускоряют вычисления

Есть ещё одна особенность Python. В обычной реализации языка (CPython) существует **GIL** (Global Interpreter Lock, «глобальная блокировка интерпретатора»). Это правило: **в каждый момент времени Python-код выполняет только один поток**, даже если ядер в процессоре много.

Откуда тогда выигрыш в примере выше? Потому что поток, который ждёт (`time.sleep`, сеть, диск), **отпускает GIL**, и другой поток спокойно работает. Потоки помогают при ожидании, то есть для I/O-bound работы.

Для вычислений (CPU-bound) картина другая. Если два потока заняты арифметикой, они по очереди берут GIL и в итоге не быстрее, чем один поток, делающий всё подряд. Чтобы по-настоящему задействовать несколько ядер, используют **процессы** (модуль `multiprocessing`): у каждого процесса свой интерпретатор и свой GIL.

Проверить это можно таким кодом:

```python
import threading, time
from multiprocessing import Process

def cpu(n=5_000_000):
    s = 0
    for i in range(n):
        s += i * i
    return s

if __name__ == "__main__":
    t = time.perf_counter(); cpu(); cpu()
    print("последовательно:", round(time.perf_counter() - t, 2))

    t = time.perf_counter()
    ths = [threading.Thread(target=cpu) for _ in range(2)]
    for th in ths: th.start()
    for th in ths: th.join()
    print("2 потока:", round(time.perf_counter() - t, 2))

    t = time.perf_counter()
    ps = [Process(target=cpu) for _ in range(2)]
    for p in ps: p.start()
    for p in ps: p.join()
    print("2 процесса:", round(time.perf_counter() - t, 2))
```

**Честная оговорка.** Среда, где я проверял примеры этого модуля, была одноядерной, поэтому этот эксперимент там ничего не показал: все три варианта вышли примерно одинаковыми (около 0.4 с), и ускорения от процессов не было — на одном ядре ему неоткуда взяться. То, что написано выше про GIL и процессы, — это общеизвестное поведение CPython, но именно эти цифры я не подтвердил измерением. Запусти код у себя на многоядерном компьютере. Ожидаемый результат: «2 потока» примерно как «последовательно», а «2 процесса» заметно быстрее, ближе к половине этого времени.

Что из этого нужно унести дальше: асинхронность (как и потоки) помогает **ждать**, но не **считать**. Тяжёлые вычисления придётся отправлять в отдельные процессы — вернёмся к этому в модуле 13.

## 3.5. Кооперативная многозадачность

Второй способ переключаться между делами — **кооперативная многозадачность**: задача сама, добровольно, говорит «сейчас я жду, можно переключиться на другого». Никто не выдёргивает её из работы насильно.

| | Вытесняющая (потоки) | Кооперативная (event loop) |
|---|---|---|
| Кто решает, когда переключиться | операционная система, в любой момент | сама задача, в заранее известных местах |
| Насколько предсказуем порядок | плохо | хорошо |
| Риск испортить общие данные | высокий | заметно ниже: задача не прерывается посреди строки |
| Цена одной «задачи» | поток ОС: память и накладные расходы | обычный объект в памяти: очень дёшево |
| Главная опасность | гонки за общие данные | задача, которая **забыла** уступить и держит всех |

Последняя строка таблицы — важная. Кооперативность держится на честности: если задача не уступает управление, остальные стоят. Сейчас мы это увидим на примере.

## 3.6. Строим свой event loop на генераторах

Вспомни модуль 1: генератор умеет остановиться на `yield` и продолжить позже с того же места, сохранив все переменные. Это и есть «приостанавливаемая функция». Значит, задачей может быть **генератор**, а `yield` — способом сказать «я жду, переключайся».

Договоримся о простом «языке»: задача делает `yield Sleep(секунды)`, что значит «разбуди меня через столько-то секунд».

```python
import time, heapq
from collections import deque

class Sleep:
    def __init__(self, seconds):
        self.seconds = seconds
```

`Sleep` — просто коробочка, в которую задача кладёт «сколько ждать».

Теперь сами задачи:

```python
def task(name, delay, steps):
    for i in range(1, steps + 1):
        print(f"[{time.perf_counter() - T0:4.2f}] {name}: шаг {i}, ухожу ждать {delay} с")
        yield Sleep(delay)
    print(f"[{time.perf_counter() - T0:4.2f}] {name}: готово")
```

Обычная функция-генератор: делает шаг, печатает время от старта (`T0`, задаём ниже) и отдаёт наружу `Sleep(delay)`. Дальше — сам цикл:

```python
def run(tasks):
    ready = deque(tasks)
    timers = []
    counter = 0
    while ready or timers:
        while ready:
            t = ready.popleft()
            try:
                cmd = next(t)
            except StopIteration:
                continue
            counter += 1
            heapq.heappush(timers, (time.perf_counter() + cmd.seconds, counter, t))
        if timers:
            when, _, t = heapq.heappop(timers)
            pause = when - time.perf_counter()
            if pause > 0:
                time.sleep(pause)
            ready.append(t)
```

Разберём по частям.

- **`ready`** — очередь задач, готовых работать прямо сейчас (`deque` из модуля-«кухни» стандартной библиотеки: быстрая двусторонняя очередь).
- **`timers`** — «список будильников»: для каждой ждущей задачи хранится момент, когда её пора разбудить. `heapq` — модуль, который держит список так, что самый ранний момент всегда достаётся первым.
- **`counter`** — просто порядковый номер, чтобы кортежи в `heapq` было с чем сравнивать, если два будильника совпадут по времени.
- **Внешний `while ready or timers`** — главный цикл: работаем, пока есть хоть что-то готовое или чего-то ожидающее.
- **Внутренний `while ready`** — даём поработать каждой готовой задаче: `next(t)` запускает генератор до ближайшего `yield`. То, что он отдал (`cmd`), — это `Sleep(...)`, и мы ставим будильник. Если генератор закончился (`StopIteration`), задача просто выбывает.
- **Блок `if timers`** — когда готовых задач больше нет, берём будильник, который сработает раньше всех, и **спим ровно до него**. Проснувшись, кладём задачу обратно в `ready`, и цикл начинается заново.

Запустим три задачи с разными задержками:

```python
T0 = time.perf_counter()
run([task("A", 0.3, 2), task("B", 0.2, 3), task("C", 0.1, 1)])
print("итого: %.2f" % (time.perf_counter() - T0))
```

Вывод:

```
[0.00] A: шаг 1, ухожу ждать 0.3 с
[0.00] B: шаг 1, ухожу ждать 0.2 с
[0.00] C: шаг 1, ухожу ждать 0.1 с
[0.10] C: готово
[0.20] B: шаг 2, ухожу ждать 0.2 с
[0.30] A: шаг 2, ухожу ждать 0.3 с
[0.40] B: шаг 3, ухожу ждать 0.2 с
[0.60] A: готово
[0.60] B: готово
итого: 0.60
```

Что тут видно:

- В момент 0.00 все три задачи сделали первый шаг и «ушли ждать». Никто не дожидался остальных.
- Дальше они просыпаются в порядке своих будильников: C в 0.10, B в 0.20, A в 0.30, и так далее. Шаги разных задач **перемешаны** — это и есть конкурентность.
- Общее время — **0.60 с**. Если бы те же задачи выполнялись строго по очереди, ушло бы 0.6 + 0.6 + 0.1 = 1.3 с. Мы уложились в время самой долгой задачи (A: две паузы по 0.3 с).

При этом поток в программе **один**. Никаких потоков ОС мы не создавали. «Официант» — это наш `while`, «заказы» — генераторы.

## 3.7. Что будет, если задача не уступает управление

Теперь покажем опасность кооперативной модели. Сделаем «плохую» задачу, которая вместо `yield Sleep(...)` использует обычный блокирующий `time.sleep`:

```python
def bad(name):
    print(f"[{time.perf_counter() - T1:4.2f}] {name}: начал")
    time.sleep(0.5)   # блокирующий вызов, а не yield Sleep
    print(f"[{time.perf_counter() - T1:4.2f}] {name}: закончил")
    yield Sleep(0)

def good(name):
    print(f"[{time.perf_counter() - T1:4.2f}] {name}: жду")
    yield Sleep(0.1)
    print(f"[{time.perf_counter() - T1:4.2f}] {name}: дождался")

T1 = time.perf_counter()
run([bad("BAD"), good("GOOD")])
```

Вывод:

```
[0.00] BAD: начал
[0.50] BAD: закончил
[0.50] GOOD: жду
[0.60] GOOD: дождался
```

Задача `GOOD` хотела всего лишь подождать 0.1 с, но **начала работу только в момент 0.50**: пока `BAD` спала «по-настоящему» через `time.sleep`, единственный поток был заморожен, и цикл не мог передать управление никому. Пятьсот миллисекунд простоя для всех.

Это в точности «миф 3» из модуля 0 (официант, который встал чистить картошку) в виде кода. И это самая частая ошибка в реальном асинхронном коде: положить внутрь задачи блокирующий вызов. Запомни правило, которое будет с нами до конца курса:

> В задаче event loop нельзя использовать блокирующие вызовы. Ожидать нужно **только** способами, которые отдают управление циклу.

Для нашего игрушечного цикла такой способ — `yield Sleep(...)`. Для настоящего `asyncio` — слово `await`, и о нём модуль 4.

## 3.8. Как настоящий цикл ждёт сеть

В нашем игрушечном цикле мы ждали только время, и просто вызывали `time.sleep(pause)`, когда ничего другого делать не было. Это допустимо: если готовых задач нет, всё равно нечего делать.

Настоящий event loop ждёт не только таймеры, но и **события ввода-вывода**: «пришли данные по сети», «сокет готов к записи». Устроено это так:

1. Цикл сообщает операционной системе: «вот список сетевых соединений, за которыми я слежу, разбуди меня, когда хоть с одним что-то произойдёт или когда наступит ближайший таймер».
2. Затем он **засыпает**, не тратя процессор.
3. Операционная система будит его, когда есть событие, и говорит, какое именно.
4. Цикл находит задачу, которая ждала это событие, и возвращает её в очередь готовых.

Для этого в ОС есть специальные вызовы (`select`, `epoll` и им подобные). Писать с ними напрямую тебе не придётся — этим занимается `asyncio`. Важно понимать принцип: **цикл не «опрашивает» соединения в бесконечной проверке, а просит систему разбудить его**. Поэтому тысяча ожидающих соединений почти ничего не стоит.

## 3.9. Что мы построили и куда идём

Сопоставим то, что мы написали, с тем, что нас ждёт в модуле 4:

| Наш игрушечный цикл | Настоящий `asyncio` |
|---|---|
| задача — генератор | задача — **корутина** (функция, объявленная через `async def`) |
| `yield Sleep(0.3)` | `await asyncio.sleep(0.3)` |
| функция `run(...)` | `asyncio.run(...)` |
| очередь `ready` и куча `timers` | то же самое, плюс слежение за сетью через ОС |
| нельзя блокировать цикл | нельзя блокировать цикл |

Настоящий `asyncio` умеет намного больше — отмену задач, таймауты, ожидание сразу нескольких результатов, работу с сетью, — но фундамент тот же: один поток, очередь готовых задач, «будильники» и приостанавливаемые функции.

## Итог модуля: словарь понятий

| Термин | Что значит |
|---|---|
| **Задача (task)** | приостанавливаемая единица работы, которую ведёт event loop |
| **Event loop (цикл событий)** | бесконечный цикл, который выбирает готовую задачу, даёт ей поработать до ближайшего ожидания и ждёт события, когда готовых нет |
| **Блокирующий вызов** | вызов, который «замораживает» поток на время ожидания (например, `time.sleep`) |
| **Поток (thread)** | отдельная нить выполнения внутри программы; переключением управляет ОС |
| **Процесс** | отдельная запущенная программа со своим интерпретатором и своей памятью |
| **GIL** | правило CPython: Python-код в каждый момент выполняет только один поток; ожидающий поток GIL отпускает |
| **Вытесняющая многозадачность** | переключение задач решает ОС, в любой момент |
| **Кооперативная многозадачность** | переключение происходит только там, где задача сама уступает управление |
| **Таймер («будильник»)** | запись «разбудить эту задачу в такое-то время» |
| **Гонка данных** | ошибка, когда результат зависит от того, в каком порядке переключились потоки |

## Чек-поинт

**1. Три «запроса» по 0.5 с выполнены последовательно и в трёх потоках. Сколько займёт каждый вариант и почему?**
Ответ: последовательно около 1.5 с (0.5 × 3), в потоках около 0.5 с: пока один поток ждёт, остальные ждут одновременно с ним.

**2. Почему два потока с тяжёлой арифметикой не дают ускорения, а два процесса дают (на многоядерной машине)?**
Ответ: из-за GIL Python-код в каждый момент выполняет только один поток. У каждого процесса свой интерпретатор и свой GIL, поэтому процессы реально работают на разных ядрах.

**3. Чем вытесняющая многозадачность отличается от кооперативной?**
Ответ: при вытесняющей переключением управляет ОС и может прервать задачу где угодно; при кооперативной задача сама указывает моменты, где можно переключиться.

**4. В нашем игрушечном цикле у задачи `BAD` стоит `time.sleep(0.5)`, а у `GOOD` — `yield Sleep(0.1)`. Почему `GOOD` начала работать только через полсекунды?**
Ответ: блокирующий `time.sleep` заморозил единственный поток, в котором работает цикл, и он не мог передать управление другой задаче, пока `BAD` не проснулась.

**5. Почему задача, которая ждёт ответа от сети, почти ничего не стоит event loop'у?**
Ответ: цикл не проверяет соединение постоянно, а просит операционную систему разбудить его при событии и засыпает; ожидающая задача — это лишь запись в памяти.

**6. Что в нашем игрушечном цикле играет роль «официанта», а что — «заказов»?**
Ответ: «официант» — цикл `while` в функции `run`, «заказы» — генераторы-задачи.
