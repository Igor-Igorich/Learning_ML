## 4.1. `async def`: корутина — это объект

Функция, объявленная через `async def`, называется **корутиной-функцией**, а то, что получается при её вызове, — **корутиной**.

```python
import asyncio, time

async def fetch(name, delay):
    print(name, "начал")
    await asyncio.sleep(delay)
    print(name, "закончил")
    return f"данные {name}"
```

Сравни с обычной функцией: добавилось слово `async` перед `def`, а внутри появилось `await`. Смысл этих слов разберём ниже. Сначала — главное свойство, о котором мы предупреждали в модуле 1:

```python
c = fetch("X", 0.1)
print(type(c))     # <class 'coroutine'>
```

**Вызов `fetch("X", 0.1)` не выполнил тело функции** — ничего не напечаталось. Мы получили объект-корутину: «заготовку работы», которая готова выполниться, но ещё не начала. Это ровно то же поведение, что у генераторной функции в модуле 1.

Если корутину создали, но никогда не запустили, Python выдаст предупреждение `RuntimeWarning: coroutine ... was never awaited`. Видишь его — значит, где-то забыт `await`.

Корутина запускается только двумя способами:

1. её ждут через `await` из другой корутины;
2. её передают в `asyncio.run(...)` или оборачивают в задачу (об этом ниже).

## 4.2. `await` и `asyncio.run`

```python
async def demo1():
    c = fetch("X", 0.1)
    print(await c)

asyncio.run(demo1())
```

Вывод:

```
X начал
X закончил
данные X
```

Разбор:

- **`await выражение`** значит: «запусти эту корутину (или дождись этого результата) и, пока она ждёт, разреши циклу событий заниматься другими задачами; когда результат будет готов — продолжи меня отсюда и подставь результат». Результат `await` — то, что корутина вернула через `return` (у нас строка `"данные X"`).
- **`await asyncio.sleep(delay)`** — асинхронный «сон». В отличие от `time.sleep`, он **не блокирует поток**: корутина ставит себе будильник и уступает управление циклу. Это прямой аналог нашего `yield Sleep(...)` из модуля 3.
- **`asyncio.run(корутина)`** — точка входа: создаёт цикл событий, выполняет переданную корутину до конца и закрывает цикл. Обычно её вызывают один раз, в самом низу программы.

Два правила, которые нужно запомнить сразу:

1. **`await` можно писать только внутри `async def`.** Вне корутины это синтаксическая ошибка.
2. **`asyncio.run` нельзя вызывать, когда цикл уже работает** (например, изнутри корутины). Внутри корутин используем `await`.

Теперь ясно, как это связано с модулем 3: `async def` — это «функция-задача», `await` — место, где задача уступает управление (как `yield`), а `asyncio.run` — наш `run(...)`.

## 4.3. Последовательно и одновременно

Самая важная разница в асинхронном коде — между «подряд» и «одновременно». Сначала — подряд:

```python
async def sequential():
    a = await fetch("A", 0.3)
    b = await fetch("B", 0.3)
```

Вывод (время от старта):

```
[0.00] A начал
[0.30] A закончил
[0.30] B начал
[0.60] B закончил
итого 0.60
```

`await` на строке с `A` заставляет функцию **дождаться результата, прежде чем идти дальше**. Асинхронность тут ничего не ускорила: каждая корутина ждёт другую. Это частая ошибка новичков: `async`/`await` сами по себе ничего не запускают одновременно.

Чтобы запустить несколько корутин **одновременно**, используем `asyncio.gather`:

```python
res = await asyncio.gather(fetch("A", 0.3), fetch("B", 0.2), fetch("C", 0.1))
print(res)
```

Вывод:

```
[0.00] A начал
[0.00] B начал
[0.00] C начал
[0.10] C закончил
[0.20] B закончил
[0.30] A закончил
['данные A', 'данные B', 'данные C']
итого 0.30
```

`gather(a, b, c)` запускает все переданные корутины как задачи, дожидается их всех и возвращает **список результатов в том же порядке, в котором мы их передали** (не в порядке завершения!). Общее время — **0.30 с**, то есть время самой долгой корутины, а не сумма 0.6 с.

Если корутин заранее неизвестное количество, их передают через звёздочку: `await asyncio.gather(*(fetch(n, 0.1) for n in names))`. `*` «распаковывает» коллекцию в отдельные аргументы.

## 4.4. Задачи: `asyncio.create_task`

**Задача (Task)** — это корутина, которую уже поставили в очередь цикла событий. Создаётся через `asyncio.create_task(...)`. Разница с простым `await`: задача **начинает выполняться «в фоне», а текущая корутина продолжает работать дальше**, не дожидаясь.

```python
async def demo3():
    t1 = asyncio.create_task(fetch("T1", 0.3))
    t2 = asyncio.create_task(fetch("T2", 0.2))
    print("задачи созданы, main ещё работает")
    await asyncio.sleep(0)
    print("после sleep(0)")
    r1 = await t1
    r2 = await t2
    print(r1, r2)
```

Вывод:

```
задачи созданы, main ещё работает
T1 начал
T2 начал
после sleep(0)
T2 закончил
T1 закончил
данные T1 данные T2
```

Обрати внимание на порядок. Сразу после `create_task` задачи **ещё не начали работу**: строка «задачи созданы» напечаталась раньше, чем «T1 начал». Задачи получают возможность запуститься только тогда, когда текущая корутина отдаёт управление циклу — здесь это `await asyncio.sleep(0)` (ожидание нулевой длины: «уступи управление и сразу вернись»). Это та самая кооперативность из модуля 3: пока текущая корутина не дошла до `await`, никто другой работать не может.

Дальше `await t1` дожидается результата задачи. Задача, в отличие от голой корутины, **уже идёт**, поэтому ожидание не запускает работу заново, а лишь дожидается финиша. Суммарное время — 0.30 с.

**Важное правило про фоновые задачи.** Если ты создаёшь задачу и нигде не сохраняешь ссылку на неё, Python может «забыть» её раньше времени (задача исчезнет из памяти до завершения). Поэтому для задач «запустил и забыл» ссылки сохраняют, например, в множестве. Мы так и сделаем в PocketML ниже.

## 4.5. Ошибки внутри `gather`

Исключение внутри корутины «всплывает» в том месте, где её ждут:

```python
async def boom():
    await asyncio.sleep(0.05)
    raise ValueError("сломалось")

try:
    await asyncio.gather(fetch("ok", 0.2), boom())
except ValueError as e:
    print("поймано:", e)
```

Вывод (опущены пометки времени):

```
ok начал
поймано: сломалось
ok закончил
```

`gather` сразу передал нам ошибку из `boom()`, и `except` сработал. Но обрати внимание на последнюю строку: **корутина `ok` не была остановлена** и спокойно дошла до конца (мы подождали 0.3 с, чтобы это увидеть). Значит, ошибка в одной корутине не отменяет остальные автоматически.

Если нужно дождаться всех и получить все результаты, включая ошибки, добавляют `return_exceptions=True`:

```python
res = await asyncio.gather(fetch("ok2", 0.1), boom(), return_exceptions=True)
print(res)   # ['данные ok2', ValueError('сломалось')]
```

Тогда исключения не летят наружу, а лежат в списке результатов на своём месте. Дальше остаётся проверить каждый элемент: результат это или ошибка.

## 4.6. Отмена и таймауты

**Отмена.** У задачи есть метод `cancel()`. Он не убивает задачу мгновенно, а «вбрасывает» в неё исключение `asyncio.CancelledError` в ближайшей точке `await`.

```python
async def slow():
    try:
        await asyncio.sleep(10)
    except asyncio.CancelledError:
        print("slow: меня отменили, убираюсь")
        raise

t = asyncio.create_task(slow())
await asyncio.sleep(0.1)
t.cancel()
try:
    await t
except asyncio.CancelledError:
    print("задача отменена, cancelled() =", t.cancelled())
```

Вывод:

```
slow: меня отменили, убираюсь
задача отменена, cancelled() = True
```

Внутри `slow` мы поймали `CancelledError`, сделали уборку и **подняли исключение снова** (`raise`). Это важно: если проглотить его, задача не завершится, и отмена будет проигнорирована. Правило: поймал `CancelledError` — прибери за собой и пробрось дальше.

**Таймауты.** Часто нужно сказать: «если не успеешь за столько-то секунд — отмени». Есть два способа:

```python
try:
    async with asyncio.timeout(0.2):
        await asyncio.sleep(5)
except TimeoutError:
    print("таймаут сработал")

try:
    await asyncio.wait_for(asyncio.sleep(5), timeout=0.2)
except TimeoutError:
    print("wait_for: таймаут")
```

Оба напечатали своё сообщение. `asyncio.timeout(...)` — это **асинхронный менеджер контекста**: всё внутри блока `async with` получает ограничение по времени. `asyncio.wait_for(корутина, timeout=...)` — то же для одной корутины. Когда время вышло, ожидающая корутина отменяется, а снаружи поднимается `TimeoutError`.

## 4.7. Ограничение параллелизма: `Semaphore`

Если запустить одновременно 1000 запросов к внешнему сервису, он может «упасть» или заблокировать нас. Нужен способ сказать: «не больше N одновременно». Для этого есть **семафор** — счётчик «пропусков».

```python
async def worker(name, sem):
    async with sem:
        print(name, "вошёл")
        await asyncio.sleep(0.2)
    print(name, "вышел")

sem = asyncio.Semaphore(2)
await asyncio.gather(*(worker(f"w{i}", sem) for i in range(4)))
```

Вывод (по времени):

```
[0.00] w0 вошёл
[0.00] w1 вошёл
[0.20] w0 вышел
[0.20] w1 вышел
[0.20] w2 вошёл
[0.20] w3 вошёл
[0.40] w2 вышел
[0.40] w3 вышел
итого 0.40
```

`Semaphore(2)` пускает внутрь блока `async with sem` не больше двух корутин одновременно. Остальные ждут на входе (и во время ожидания цикл занимается другими делами). Четыре работы по 0.2 с уложились в 0.4 с — две волны по два.

(Есть и `asyncio.Lock` — «семафор на одного». Он нужен, когда несколько корутин меняют общие данные и между чтением и записью есть `await`. Пока нам это не нужно, вернёмся при необходимости.)

## 4.8. `async with` и `async for`

В модуле 2 мы упоминали асинхронный `with`, а в модуле 1 — итераторы. Асинхронные версии устроены так же, только методы асинхронные:

| Обычная конструкция | Асинхронная | Методы |
|---|---|---|
| `with` | `async with` | `__aenter__`, `__aexit__` (их можно `await`-ить) |
| `for` | `async for` | `__aiter__`, `__anext__` |
| генератор (`yield`) | асинхронный генератор (`async def` + `yield`) | — |

```python
class Res:
    async def __aenter__(self):
        print("aenter"); await asyncio.sleep(0.05); return self
    async def __aexit__(self, a, b, c):
        print("aexit"); await asyncio.sleep(0.05); return False

async def ticker(n):
    for i in range(n):
        await asyncio.sleep(0.05)
        yield i

async with Res() as r:
    print("внутри")

async for i in ticker(3):
    print("tick", i)

print([x async for x in ticker(3)])
```

Вывод:

```
aenter
внутри
aexit
tick 0
tick 1
tick 2
[0, 1, 2]
```

Смысл: подготовка и уборка (`__aenter__`, `__aexit__`) сами могут ждать — например, открытие соединения с базой данных — и на это время цикл свободен. `async for` берёт следующий элемент, который может «прийти» не сразу (например, очередная порция данных из сети). `ticker` — асинхронный генератор: `yield` отдаёт значения, а `await` внутри позволяет ждать между ними. Списковое включение тоже может быть асинхронным: `[x async for x in ticker(3)]`.

Правило запоминания простое: **если для объекта в документации сказано «используй `async with` / `async for`», то пишем именно так**, обычный `with`/`for` не сработает.

## 4.9. Главная ошибка: блокирующий код внутри корутины

Вернёмся к модулю 3, где `time.sleep` внутри задачи заморозил весь цикл. Проверим то же самое на настоящем `asyncio`. Запустим «пульс», который печатается каждые 0.05 с, рядом с корутиной, делающей блокирующий `time.sleep(0.3)`:

```python
async def heartbeat():
    for _ in range(6):
        print("пульс")
        await asyncio.sleep(0.05)

async def blocking():
    time.sleep(0.3)          # блокирующий вызов внутри async def!

await asyncio.gather(heartbeat(), blocking())
```

Вывод (время от старта):

```
[0.00] пульс
[0.30] пульс
[0.35] пульс
[0.40] пульс
[0.45] пульс
[0.50] пульс
```

Пульс должен был идти каждые 0.05 с, но между первым и вторым ударом **0.3 секунды тишины**: пока `blocking` стояла на `time.sleep`, цикл был заморожен. Это тот самый «официант, который встал чистить картошку».

Как исправить, если блокирующий вызов нельзя заменить асинхронным (например, старая библиотека)? Отправить его в **отдельный поток** через `asyncio.to_thread`:

```python
async def offloaded():
    await asyncio.to_thread(time.sleep, 0.3)

await asyncio.gather(heartbeat(), offloaded())
```

Вывод:

```
[0.00] пульс
[0.05] пульс
[0.10] пульс
[0.15] пульс
[0.20] пульс
[0.25] пульс
```

Теперь пульс идёт ровно, потому что блокирующий вызов «уехал» в другой поток, а цикл остался свободным. Поток, ожидающий на `time.sleep`, отпускает GIL (модуль 3), поэтому всё работает.

Границы применимости:

- `asyncio.to_thread` спасает от **блокирующего ожидания** (I/O-bound). Для **тяжёлых вычислений** (CPU-bound) поток не поможет из-за GIL: нужны отдельные процессы. Этому посвящён модуль 13.
- Всегда лучше искать **асинхронную** библиотеку для нужной задачи (для баз данных, HTTP-запросов и так далее) — мы будем использовать именно такие.

## 4.10. PocketML, версия 1

Соберём первую версию сквозного проекта. Пока у нас нет ни веб-сервера, ни базы данных, поэтому это просто программа на `asyncio`, но с той логикой, которая потом переедет в веб-API:

- сервис **быстро принимает** задание и сразу возвращает его идентификатор;
- «обработка» идёт **в фоне** (пока это имитация ожидания вместо настоящей модели);
- статус задания можно узнать в любой момент: `queued` → `running` → `done` (или `failed`).

```python
import asyncio
import time
import uuid

jobs = {}  # job_id -> {"status": ..., "result": ...}
background_tasks = set()  # держим ссылки на фоновые задачи

async def fake_model(payload: str) -> str:
    """Имитация тяжёлого ожидания: настоящей работы тут нет."""
    await asyncio.sleep(0.5)
    return payload.upper()

async def process_job(job_id: str, payload: str) -> None:
    jobs[job_id]["status"] = "running"
    try:
        jobs[job_id]["result"] = await fake_model(payload)
        jobs[job_id]["status"] = "done"
    except Exception as exc:
        jobs[job_id]["status"] = "failed"
        jobs[job_id]["result"] = str(exc)

async def submit(payload: str) -> str:
    job_id = uuid.uuid4().hex[:6]
    jobs[job_id] = {"status": "queued", "result": None}
    task = asyncio.create_task(process_job(job_id, payload))
    background_tasks.add(task)
    task.add_done_callback(background_tasks.discard)
    return job_id

async def main():
    t0 = time.perf_counter()
    ids = [await submit(text) for text in ["привет", "мир", "async", "pocket", "ml"]]
    print("принято за %.3f с, id: %d штук" % (time.perf_counter() - t0, len(ids)))
    print("сразу после приёма:", {jobs[i]["status"] for i in ids})
    await asyncio.sleep(0.1)
    print("через 0.1 с:", {jobs[i]["status"] for i in ids})
    await asyncio.sleep(0.5)
    print("через 0.6 с:", {jobs[i]["status"] for i in ids})
    print(sorted(jobs[i]["result"] for i in ids))
    print("всего %.2f с" % (time.perf_counter() - t0))

asyncio.run(main())
```

Код лежит отдельным файлом `pocketml_v1.py` рядом с этим модулем. Вывод:

```
принято за 0.000 с, id: 5 штук
сразу после приёма: {'queued'}
через 0.1 с: {'running'}
через 0.6 с: {'done'}
['ASYNC', 'ML', 'POCKET', 'МИР', 'ПРИВЕТ']
всего 0.60 с
```

Разбор по частям:

- **`jobs`** — обычный словарь-«склад» заданий. Позже его заменит база данных.
- **`fake_model`** — заглушка модели: ждёт полсекунды и возвращает текст заглавными буквами. Слово `async` и `await asyncio.sleep` здесь показывают, что настоящая модель тоже «занимает время», но в реальности её вызов будет иметь другую природу (модуль 13).
- **`process_job`** — вся жизнь задания: ставит статус `running`, выполняет «модель», записывает результат и статус `done`. Обёртка `try/except` гарантирует, что при ошибке задание получит статус `failed`, а не «зависнет».
- **`submit`** — то, что позже станет ответом веб-сервера на запрос: создаёт запись со статусом `queued`, запускает обработку **как фоновую задачу** через `create_task` и **сразу возвращает идентификатор**, не дожидаясь результата. `background_tasks` и `add_done_callback(...discard)` — тот самый приём с сохранением ссылки: пока задача идёт, ссылка есть, а когда она завершилась, ссылка удаляется.
- **`main`** — «клиент»: подаёт пять заданий, смотрит статусы в разные моменты времени.

Что мы видим в выводе:

- Приём пяти заданий занял **0.000 с** — сервис не заставляет клиента ждать обработки.
- Сразу после приёма все пять в статусе `queued` (задачи созданы, но ещё не стартовали — вспомни `await asyncio.sleep(0)` из пункта 4.4), через 0.1 с — все `running`, через 0.6 с — все `done`.
- Все пять «обработок» по 0.5 с прошли **одновременно**, общее время — 0.60 с (0.5 с обработки + 0.1 с нашей паузы). Последовательно ушло бы 2.5 с.

Это уже тот самый «официант, ведущий много заказов сразу». В модуле 6 у него появится «зал»: настоящий веб-API на FastAPI.

## Итог модуля: словарь понятий

| Термин | Что значит |
|---|---|
| **`async def`** | объявление корутины-функции; вызов возвращает объект-корутину и не выполняет тело |
| **Корутина** | «заготовка работы», которая выполняется только когда её запустили (`await`, `asyncio.run`, задача) |
| **`await`** | «дождись результата и, пока ждёшь, разреши циклу заниматься другим»; разрешён только внутри `async def` |
| **`asyncio.run`** | запуск цикла событий и выполнение корутины до конца; используется в точке входа |
| **`asyncio.sleep`** | асинхронное ожидание; в отличие от `time.sleep` не блокирует цикл |
| **Task (задача)** | корутина, поставленная в очередь цикла; начинает работу, когда текущая корутина уступит управление |
| **`asyncio.gather`** | запускает несколько корутин одновременно и возвращает список результатов в порядке передачи |
| **`return_exceptions=True`** | режим `gather`, при котором ошибки попадают в список результатов, а не вылетают наружу |
| **`task.cancel()` / `CancelledError`** | отмена задачи; пойманный `CancelledError` нужно пробрасывать дальше |
| **`asyncio.timeout` / `wait_for`** | ограничение времени ожидания; при превышении поднимается `TimeoutError` |
| **`Semaphore`** | счётчик, ограничивающий число одновременных «входов» в блок |
| **`async with` / `async for`** | асинхронные версии `with` и `for` (`__aenter__`/`__aexit__`, `__aiter__`/`__anext__`) |
| **`asyncio.to_thread`** | запуск блокирующей функции в отдельном потоке, чтобы не замораживать цикл |

## Чек-поинт

**1. Что произойдёт при вызове `fetch("X", 0.1)`, если `fetch` объявлена через `async def`, и мы нигде не написали `await`?**
Ответ: тело функции не выполнится; будет создан объект-корутина, а Python при завершении выдаст предупреждение «coroutine was never awaited».

**2. Чем отличаются два фрагмента по времени, если `fetch` ждёт 0.3 с каждая?**
```python
a = await fetch("A", 0.3)
b = await fetch("B", 0.3)
```
```python
a, b = await asyncio.gather(fetch("A", 0.3), fetch("B", 0.3))
```
Ответ: первый занимает около 0.6 с (корутины выполняются одна за другой), второй — около 0.3 с (выполняются одновременно).

**3. В каком порядке `gather` возвращает результаты: по завершению или по порядку передачи?**
Ответ: по порядку передачи, независимо от того, какая корутина закончила раньше.

**4. Почему сразу после `asyncio.create_task(...)` задача ещё не начала выполняться?**
Ответ: задача запускается, когда текущая корутина уступает управление циклу (например, доходит до `await`). Пока этого не произошло, цикл занят текущей корутиной.

**5. Что нужно сделать, поймав `asyncio.CancelledError`, и почему?**
Ответ: сделать необходимую уборку и поднять исключение снова (`raise`). Иначе отмена будет проигнорирована и задача не завершится.

**6. Что случится с частотой «пульса», если внутри `async def` вызвать `time.sleep(0.3)`? Чем это исправить?**
Ответ: на 0.3 с весь цикл замрёт, и «пульс» встанет. Исправление: использовать `await asyncio.sleep(0.3)` или, если блокирующий вызов заменить нельзя, `await asyncio.to_thread(...)`.

**7. Зачем в PocketML хранится множество `background_tasks`?**
Ответ: чтобы у фоновых задач всегда была ссылка, пока они работают: задача без ссылки может быть уничтожена до завершения. После окончания задачи ссылка удаляется через `add_done_callback`.

**8. Поможет ли `asyncio.to_thread` ускорить долгий математический расчёт?**
Ответ: нет. Из-за GIL потоки не ускоряют вычисления на Python; для CPU-bound работы нужны процессы (тема модуля 13). `to_thread` спасает от блокирующего ожидания, но не от тяжёлых расчётов.
