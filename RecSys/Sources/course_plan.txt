## Модуль 1. Введение: что такое рекомендации и зачем они нужны

### 1.1 Суть рекомендательной системы
- Определение с нуля: система, которая предсказывает, какие объекты (товары, фильмы, треки, банковские продукты) понравятся конкретному пользователю.
- Разница «поиск vs рекомендация»: в поиске пользователь знает, чего хочет («фильм Нолана»); в рекомендации — нет («посоветуй что-нибудь»).
- Где встречаются: Netflix, Spotify, YouTube, Amazon, Wildberries, Т-Банк (рекомендации кредитных карт, вкладов, инвестпродуктов), Avito.

### 1.2 Типы рекомендательных систем

| Тип | Принцип | Пример |
|:---|:---|:---|
| Коллаборативная фильтрация | Люди похожи на людей | «Пользователи, похожие на вас, купили…» |
| Контентная фильтрация | Товары похожи на товары | «Похоже на то, что вы смотрели» |
| Гибридная | Комбинация двух выше | Современные production-системы |
| На основе знаний (Knowledge-based) | Жёсткие правила | «Если возраст > 60 → рекомендовать ОСАГО» |

### 1.3 Постановка задачи: explicit vs implicit feedback
- **Explicit feedback:** пользователь явно ставит оценку (звёзды 1–5, лайк/дизлайк).
- **Implicit feedback:** поведение говорит само за себя (просмотр, клик, время на странице, покупка, добавление в корзину).
- **Rating prediction:** предсказать оценку (например, 4.5 из 5).
- **Ranking (Top-K):** выдать список из K лучших товаров — главная задача в production.

### 1.4 Матрица взаимодействий User-Item
- Представление: строки = пользователи, столбцы = товары, ячейки = рейтинг/факт взаимодействия.
- Разреженность (Sparsity): если 100K пользователей и 10K фильмов, а каждый пользователь посмотрел 100 фильмов — матрица заполнена лишь на 0.1%. Это главная структурная проблема, влияющая на выбор всех дальнейших алгоритмов.

### 1.5 Ключевые проблемы рекомендательных систем
- **Cold Start:** новый пользователь (нет истории) или новый товар (нет взаимодействий).
- **Scalability:** 100M пользователей × 10M товаров — невозможно обрабатывать наивно.
- **Popularity Bias:** модель рекомендует только топ-10 популярных, игнорируя нишевое.
- **Grey Sheep:** пользователи с непредсказуемыми вкусами, для которых нет похожих людей.
- **Serendipity:** способность удивить приятной неожиданностью, а не только точным совпадением с прошлым.

### 1.6 Практика
- Загрузить датасет MovieLens 1M.
- Посчитать разреженность матрицы: `1 - (nonzero / (users × items))`.
- Построить гистограмму распределения рейтингов.
- Найти «супер-активных» и «супер-неактивных» пользователей (по числу оценок).

## Модуль 2. Математические основы: сходство, расстояния и нормализация

### 2.1 Разреженные матрицы
- Почему хранить полную матрицу невозможно: 100M × 10M ячеек — это терабайты в основном нулевых значений.
- Форматы хранения: **COO** (координаты ненулевых элементов), **CSR** (Compressed Sparse Row) — компактное построчное хранение, удобное для матричных операций.
- В Python: `scipy.sparse.csr_matrix`.

### 2.2 Меры сходства (Similarity Metrics)
Каждая мера — с формулой, примером и интерпретацией.

**Косинусное сходство (Cosine Similarity)**
- Формула: `cos(A,B) = (A·B) / (||A|| × ||B||)`
- Интерпретация: угол между векторами. 1 = одинаковые вкусы, 0 = ортогональны, −1 = противоположны.
- Проблема: игнорирует масштаб (пользователь, ставящий всем 5, будет казаться похожим на строгого критика, если оба ставят оценки в одной пропорции).

**Корреляция Пирсона (Pearson Correlation)**
- Формула: косинусное сходство после mean-centering (вычитания среднего рейтинга каждого пользователя).
- Интерпретация: учитывает «щедрость» пользователя — два человека с разными средними оценками могут быть похожи по относительным предпочтениям.
- Проблема: нестабильна при малом числе общих оценённых товаров.

**Евклидово расстояние**
- Формула: `sqrt(Σ(Ai - Bi)²)`
- Проблема: в высоких размерностях (10K+ товаров) все расстояния становятся похожими друг на друга — «проклятие размерности» (curse of dimensionality).

**Сходство Жаккара (Jaccard Similarity)**
- Формула: `|A ∩ B| / |A ∪ B|`
- Применение: бинарные данные (купил/не купил, посмотрел/не посмотрел).
- Не учитывает «насколько сильно» понравилось — только факт взаимодействия.

### 2.3 Нормализация рейтингов
- **Mean-centering:** вычитаем средний рейтинг пользователя. Зачем: один пользователь щедрый (ставит 4–5 всем), другой строгий (ставит 1–2 всем) — без нормализации они кажутся непохожими, хотя относительные предпочтения могут совпадать.
- **Z-score:** `(rating - mean) / std` — дополнительно учитывает разброс оценок пользователя, а не только смещение.
- Когда нормализовать: почти всегда в User-Based CF; в Item-Based — по ситуации (иногда используют adjusted cosine — тот же mean-centering, но по строкам).

### 2.4 Практика
- Реализовать все 4 меры сходства на чистом NumPy (векторизованно, без циклов).
- Найти 5 ближайших соседей для одного пользователя по косинусу и по Пирсону — сравнить, чем отличаются результаты.
- Построить heatmap матрицы сходства для 20 случайных пользователей.

## Модуль 3. Коллаборативная фильтрация: User-Based (UB-CF)

### 3.1 Идея, объяснённая на аналогии
«Если Алиса и Боб смотрят одни и те же фильмы и ставят им похожие оценки, то фильм, который понравился Бобу, скорее всего понравится и Алисе».
Это **memory-based** подход: модель ничему не «обучается» заранее — на каждый запрос ищутся похожие пользователи заново (или по предвычисленной матрице).

### 3.2 Алгоритм по шагам
1. Найти всех пользователей, у которых есть пересечение по оценённым товарам с целевым пользователем.
2. Посчитать сходство (косинус или Пирсон, Модуль 2) между целевым пользователем и каждым из них.
3. Выбрать k ближайших соседей (k-NN).
4. Для товара, который целевой пользователь ещё не оценил, сделать взвешенное предсказание:

```
pred(u, i) = mean_u + Σ(sim(u,v) × (rating(v,i) - mean_v)) / Σ|sim(u,v)|
```

где суммирование идёт по соседям `v`, которые оценили товар `i`.

### 3.3 Проблемы User-Based
- **Сложность:** `O(N² × M)` — для каждого пользователя нужно искать похожих среди миллионов.
- **Нестабильность:** предпочтения пользователей меняются быстрее, чем свойства товаров.
- **Холодный старт пользователя:** у нового пользователя нет соседей.
- **Холодный старт товара:** если товар никто не оценил, для него нельзя ничего предсказать.

### 3.4 Практика
Полная ручная реализация на Pandas:
- Построить матрицу user-item.
- Реализовать функцию `find_neighbors(user_id, k, metric)`.
- Реализовать функцию `predict_rating(user_id, item_id, neighbors)`.
- Подобрать оптимальное `k` через кросс-валидацию (k = 5, 10, 20, 50).
- Сравнить косинус vs Пирсон на одних и тех же данных по RMSE.

## Модуль 4. Коллаборативная фильтрация: Item-Based (IB-CF)

### 4.1 Идея и ключевой инсайт
«Если пользователь любил "Матрицу" и "Бегущего по лезвию", а "Начало" похоже на них — порекомендуем "Начало"».
Главное отличие от Модуля 3: ищем похожие **товары**, а не похожих людей.

### 4.2 Почему Item-Based лучше User-Based в production

| Аспект | User-Based | Item-Based |
|:---|:---|:---|
| Стабильность | Пользователи меняют вкусы | Свойства товаров стабильны |
| Масштабируемость | `O(N²M)` — плохо при N (пользователей) ≫ M (товаров) | `O(M²)` — лучше, если M < N |
| Кэширование | Практически невозможно (соседи меняются часто) | Матрица сходства товаров кэшируется и пересчитывается редко |
| Реальный пример | Используется реже | Amazon использует именно IB-CF ещё с 2003 года |

### 4.3 Алгоритм
1. Предвычислить матрицу сходства всех пар товаров (косинус или adjusted cosine).
2. Для целевого пользователя найти товары, похожие на те, что он уже оценил высоко.
3. Предсказание — взвешенное среднее оценок пользователя, взвешенное сходством товаров:

```
pred(u, i) = Σ(sim(i,j) × rating(u,j)) / Σ|sim(i,j)|
```

### 4.4 Предвычисление и кэширование
- Матрица сходства товаров пересчитывается раз в сутки (batch-job), а не в реальном времени.
- В момент запроса — только lookup в готовой матрице: `O(1)` на товар.
- Именно это делает Item-Based подход масштабируемым до миллионов пользователей при разумной latency.

### 4.5 Практика
- Реализовать Item-Based на Pandas с предвычислением матрицы сходства.
- Сравнить скорость инференса: User-Based (пересчёт при каждом запросе) vs Item-Based (готовый кэш).
- Эксперимент: скрыть 20% оценок пользователя, предсказать их, сравнить с реальными значениями через RMSE.

## Модуль 5. Матричная факторизация: скрытые факторы (SVD, ALS, BPR)

### 5.1 Проблема размерности
Матрица 100K пользователей × 10K фильмов = 1 млрд ячеек. Нужно «сжать» эту информацию в компактное представление, а не хранить и сравнивать всё напрямую (как в Модулях 3–4).

### 5.2 Идея скрытых факторов (Latent Factors)
- Каждый пользователь — вектор в пространстве скрытых факторов: `[любит_боевики: 0.8, любит_мелодрамы: -0.3, любит_комедии: 0.5, ...]`.
- Каждый товар — тоже вектор в том же пространстве: `[боевик: 0.9, мелодрама: 0.1, комедия: 0.4, ...]`.
- Предсказанный рейтинг = скалярное произведение этих векторов.
- Размерность векторов — гиперпараметр, обычно 50–200 (вместо исходных 10K измерений).

### 5.3 SVD (Singular Value Decomposition)
- Математика: любую матрицу `R` можно разложить как `R = U × Σ × Vᵀ`, где `U` — пользователи в скрытом пространстве, `V` — товары, `Σ` — диагональная матрица весов факторов (опирается на вашу уже сильную линейную алгебру).
- Проблема: классический SVD требует полностью заполненной матрицы — пропуски нельзя просто заменить нулями (это исказит результат, введя ложный сигнал «оценка = 0»).
- Практическое решение: Truncated SVD на разреженной матрице (`scipy.sparse.linalg.svds`) или переход к Funk SVD (следующий пункт).

### 5.4 Funk SVD и обучение через градиентный спуск
- Идея: не решать SVD аналитически, а **обучать** векторы `p_u` (пользователь) и `q_i` (товар) градиентным спуском, минимизируя ошибку только на известных рейтингах:

```
min Σ(r_ui - p_u·q_i)² + λ(||p_u||² + ||q_i||²)
```

- Регуляризационный член `λ(...)` — та же идея L2/Ridge, что вы уже проходили для логистической регрессии.

### 5.5 ALS (Alternating Least Squares)
- Идея: поочерёдно фиксируем векторы пользователей и решаем задачу наименьших квадратов для векторов товаров, затем наоборот.
- Почему работает: при фиксированных `p_u` оптимизация по `q_i` — обычная линейная регрессия, для которой есть точное аналитическое решение (в отличие от градиентного спуска в Funk SVD).
- Почему хорошо масштабируется: шаги для разных пользователей независимы друг от друга — это идеально ложится на параллельные вычисления (например, Spark ALS).
- Для **implicit feedback** используется взвешенная версия (Hu, Koren, Volinsky, 2008): вводится вес уверенности `c_ui = 1 + α · r_ui`, где `r_ui` — число взаимодействий. Чем больше взаимодействий — тем больше доверия, что сигнал реальный, а не случайность.

### 5.6 BPR (Bayesian Personalized Ranking)
- Постановка для implicit feedback: явных отрицательных оценок нет, есть только факты взаимодействия.
- Идея: пользователь предпочёл товар `i` (с которым взаимодействовал) товару `j` (который не видел/не купил) — обучаем модель на **относительном порядке пар**, а не на абсолютных значениях.
- Функция потерь: максимизировать вероятность того, что модель предскажет `p_u·q_i > p_u·q_j` для наблюдаемой пары.
- Почему BPR часто лучше обычного ALS для implicit-задач: он напрямую оптимизирует то, что нужно бизнесу (правильный порядок), а не прокси-метрику (точность предсказания «рейтинга»).

### 5.7 Практика
- Библиотека `surprise`: `SVD` (Funk SVD с градиентным спуском), `NMF` (Non-negative Matrix Factorization).
- Библиотека `implicit`: `ALS` для implicit feedback, `BPR` для pairwise-ранжирования.
- Сравнить RMSE / Precision@10 на MovieLens для SVD, ALS и BPR на одном и том же train/test split (используя методологию из общего плана — temporal split, а не случайный).

## Модуль 6. Контентная фильтрация (Content-Based)

### 6.1 Идея
«Рекомендуем товары, похожие на те, что пользователь уже полюбил».
- Плюс: не нужны данные о других пользователях — работает с первого дня существования товара (нет cold start для новых items).
- Минус: не находит неожиданных связей («фильм про космос похож на другой фильм про космос» — предсказуемо и скучно, низкая serendipity).

### 6.2 Профиль товара (Item Profile)
- Текстовые признаки: название, описание, жанры, теги.
- Числовые признаки: год выпуска, цена, рейтинг критиков.
- Категориальные признаки: категория, бренд, режиссёр, исполнитель.

### 6.3 TF-IDF: от текста к вектору
- **Term Frequency (TF):** как часто слово встречается в описании конкретного товара.
- **Inverse Document Frequency (IDF):** `log(N / df)` — редкие слова важнее частых («фильм» встречается почти везде и малоинформативно, «киберпанк» — редко и потому значимо).
- **TF-IDF вектор:** произведение TF × IDF для каждого слова словаря.
- В Python: `sklearn.feature_extraction.text.TfidfVectorizer`.

### 6.4 Профиль пользователя (User Profile)
- Вектор пользователя = взвешенная сумма TF-IDF векторов товаров, которые ему понравились.
- Веса — оценки пользователя (или бинарные: 1 = взаимодействовал).
- Предсказание — косинусное сходство между профилем пользователя и профилем товара (Модуль 2).

### 6.5 Практика
- Построить контентную модель на MovieLens: жанры как One-Hot признаки, год выпуска — числовой признак.
- Реализовать класс `ContentBasedRecommender` с методами `fit()` и `recommend(user_id, k)`.
- Сравнить с Item-Based CF (Модуль 4): какие фильмы рекомендуются, чем и почему они отличаются.

## Модуль 7. Гибридные системы

### 7.1 Зачем нужны гибриды

| Проблема | Решение |
|:---|:---|
| Новый товар в коллаборативной модели | Контентные фичи спасают (Модуль 6 работает без истории взаимодействий) |
| Новый пользователь в контентной модели | Популярное + коллаборативное как fallback |
| Скучные рекомендации в контентной модели | Коллаборативное добавляет неожиданность (serendipity) |

### 7.2 Типы гибридных архитектур
- **Weighted:** `score = α × score_collab + (1-α) × score_content` — коэффициент α подбирается.
- **Switching:** для новых пользователей используется контентная модель, для «тёплых» — коллаборативная.
- **Feature Combination:** контентные фичи (жанры, TF-IDF) добавляются как дополнительные входы в матричную факторизацию.
- **Meta-level:** результат коллаборативной модели (эмбеддинги пользователей/товаров) становится входом для отдельной нейросети.
- **Cascade:** сначала коллаборативная модель отбирает, скажем, 100 кандидатов, затем контентная модель их ранжирует — прообраз двухстадийной архитектуры (Модуль 11).

### 7.3 Практика
- Реализовать Weighted Hybrid с подбором α через кросс-валидацию.
- Построить график `RMSE vs α`, α ∈ [0, 1].
- Реализовать Switching Hybrid: если у пользователя менее 5 оценок — используем контентную модель, иначе — коллаборативную.

## Модуль 8. Метрики: как измерять качество рекомендаций

### 8.1 Почему обычные метрики не подходят
- Accuracy бессмысленна: мы не классифицируем один объект, мы ранжируем список.
- Нужны метрики, которые учитывают **порядок** элементов в выдаче — этого не делает ни одна метрика классификации, с которыми вы уже работали.

### 8.2 Precision@K и Recall@K
- **Precision@K** = релевантных в топ-K / K. Пример: из 10 рекомендованных фильмов пользователю понравились 3 → `Precision@10 = 0.3`.
- **Recall@K** = релевантных в топ-K / всего релевантных у пользователя. Пример: пользователю нравится 20 фильмов, из них 3 попали в топ-10 → `Recall@10 = 0.15`.
- Trade-off: при увеличении K Recall растёт, Precision обычно падает.

### 8.3 F1@K
Гармоническое среднее: `2 × Precision@K × Recall@K / (Precision@K + Recall@K)`.

### 8.4 MAP (Mean Average Precision)
- **AP (Average Precision)** для одного пользователя: берём позиции релевантных товаров в списке, на каждой такой позиции считаем `Precision@pos`, усредняем эти значения.
- **MAP** = среднее AP по всем пользователям.
- Почему хорош: учитывает порядок — чем выше релевантные товары в списке, тем выше AP.

### 8.5 NDCG (Normalized Discounted Cumulative Gain) — золотой стандарт
- **CG (Cumulative Gain):** сумма релевантностей элементов в топ-K, без учёта позиции.
- **DCG:** релевантность элемента на позиции `i` делится на `log2(i+1)` — чем ниже элемент в списке, тем меньше его вклад в метрику.
- **IDCG:** DCG идеального ранжирования (все релевантные элементы стоят сверху).
- `NDCG = DCG / IDCG` — нормировано от 0 до 1, что удобно для сравнения между пользователями и моделями.

### 8.6 MRR (Mean Reciprocal Rank)
Для задач «найти хотя бы один правильный ответ»:
- `RR = 1 / rank_первого_релевантного_элемента`
- `MRR` = среднее RR по всем пользователям.

### 8.7 Дополнительные метрики качества списка
- **Coverage:** какой процент каталога система вообще способна порекомендовать (не только топ-1%).
- **Diversity:** среднее расстояние между рекомендованными товарами внутри одного списка (не хотим 5 фильмов одного жанра подряд).
- **Novelty:** насколько рекомендованные товары непопулярны (мера «сюрприза»).
- **Serendipity:** `relevance × unexpectedness` — одновременно релевантно И неожиданно.

### 8.8 Практика
- Реализовать все метрики с нуля на чистом Python (без сторонних библиотек метрик).
- Сравнить 3 модели (User-Based, Item-Based, SVD/ALS) по Precision@10, Recall@10, MAP, NDCG на одном и том же test-сете.
- Убедиться, что разные метрики выбирают разных «победителей» — обсудить, почему так происходит (связь с бизнес-смыслом метрик, которую вы уже разбирали для классификации).

## Модуль 9. Learning to Rank: ML, который учится ранжировать

### 9.1 Постановка задачи
Не предсказать рейтинг конкретного товара, а правильно **упорядочить** список товаров для пользователя.
Вход: тройки `(пользователь, товар, признаки)` → выход: ранг/оценка релевантности.

### 9.2 Pointwise подход
- Каждый товар оценивается независимо от других: предсказываем его «релевантность» как обычную регрессию/классификацию.
- Модели: логистическая регрессия, MSE-регрессия, градиентный бустинг.
- Проблема: не учитывает относительный порядок. Два товара с оценками 4.0 и 4.1 — какой должен быть выше в списке? Модели, обученной поточечно, это не важно, хотя для качества выдачи это критично.

### 9.3 Pairwise подход
- **RankNet:** сравниваем пары документов для одного запроса/пользователя, функция потерь — кросс-энтропия на вероятности «A релевантнее B».
- **BPR (Bayesian Personalized Ranking)** — тот же приём, что в Модуле 5, только теперь рассматриваемый как общий класс pairwise-методов: для пользователя `u` берём товар `i` (взаимодействовал) и товар `j` (не взаимодействовал), минимизируем `-log(σ(p_u·q_i - p_u·q_j))`.

### 9.4 Listwise подход
- **LambdaMART:** градиентный бустинг, напрямую оптимизирующий NDCG для всего списка целиком, а не отдельные пары или точки.
- «Lambda» — псевдо-градиент, показывающий, как изменение оценки одного документа повлияет на NDCG всего списка.
- Industry standard для поисковых и рекомендательных систем (используется в Yandex, Google, Amazon).

### 9.5 Практика
- LightGBM с `objective='lambdarank'`.
- Подготовка данных: параметр `group` — какие строки (товары) относятся к одному пользователю/запросу.
- Сравнить pointwise (обычный MSE/logloss), pairwise (RankNet-подобный подход) и listwise (LambdaMART) по метрике NDCG на одинаковых данных.

## Модуль 10. Эмбеддинги и нейросетевые рекомендации

### 10.1 От матричной факторизации к эмбеддингам
- Эмбеддинг — это плотный вектор в низкоразмерном пространстве (обычно 50–300 измерений).
- В матричной факторизации (Модуль 5) `p_u` и `q_i` — это уже и есть эмбеддинги, только обученные простым линейным методом.
- Нейросети учат эмбеддинги «глубже»: способны учитывать контекст, последовательность действий, контент товара — то, что линейная факторизация не умеет.

### 10.2 Item2Vec
- Аналогия с Word2Vec: если «корзина покупок» = «предложение», то «товары» = «слова».
- Skip-gram: модель учится предсказывать соседние товары по «корзине» (или сессии просмотра).
- Результат: векторы товаров, в которых близко расположены «пиво» и «чипсы», «подгузники» и «детское питание» — паттерны совместного потребления, извлечённые без явной разметки.

### 10.3 Two-Tower модели (DSSM — Deep Structured Semantic Models)
- **User Tower:** вход = ID пользователя + демография + история действий → выход = вектор `u`.
- **Item Tower:** вход = ID товара + категория + описание → выход = вектор `v`.
- Релевантность = скалярное произведение (или косинус) `u · v`.
- Ключевое преимущество: векторы товаров можно вычислить заранее (офлайн) и сложить в индекс (FAISS, Модуль 11). В момент запроса нужен только один forward pass по пользовательской башне — это и делает Two-Tower архитектуру основой быстрого Retrieval в production.
- *Примечание по последовательности изучения:* полноценная реализация Two-Tower требует PyTorch (nn.Module, autograd) — если эта тема ещё не пройдена по общему плану, на данном этапе достаточно понять принцип концептуально и вернуться к практике позже.

### 10.4 Deep Neural Networks for YouTube Recommendations (классическая статья Google, 2016)
- **Candidate Generation (Retrieval):** Two-Tower-подобная модель, отбирает сотни кандидатов из миллионов.
- **Ranking:** отдельная глубокая сеть с сотнями признаков (пользователь, товар, контекст, история взаимодействий).
- Почему две отдельные модели: кандидатная должна быть очень быстрой (работает с миллионами товаров), ранжирующая — точной (работает только с сотнями уже отобранных кандидатов). Это прямо предвосхищает архитектуру Модуля 11.

### 10.5 Практика
- Реализовать простую Two-Tower модель на PyTorch (после/параллельно с изучением основ PyTorch по общему плану):
  - `UserTower`: `Embedding(user_id) → Linear(64) → ReLU → Linear(32)`.
  - `ItemTower`: `Embedding(item_id) + Linear(признаки категории) → Linear(32)`.
  - Loss: MSE между `dot(u, v)` и рейтингом, либо BPR loss (Модуль 9.3).
- Обучить на MovieLens.
- Визуализировать эмбеддинги товаров через t-SNE — увидеть, как формируются кластеры по жанрам без явной разметки.

## Модуль 11. Двухстадийные системы: Retrieval + Ranking + Re-ranking

### 11.1 Почему одна модель не справляется
Каталог может содержать 10M+ товаров. Прогнать через тяжёлую точную модель каждый товар для каждого запроса — невозможно уложиться в бюджет latency (обычно десятки миллисекунд). Решение: несколько последовательных стадий, каждая следующая — медленнее, но точнее и работает с меньшим числом кандидатов.

### 11.2 Stage 1: Retrieval (отбор кандидатов)
Задача: из 10M товаров быстро отобрать ~1000 потенциально релевантных. Методы:
- Коллаборативная фильтрация с предвычисленными похожими товарами (Модуль 4).
- Эмбеддинги + ANN — поиск ближайших векторов (следующий пункт).
- Популярное и тренды — как fallback, особенно для cold start (Модуль 12).
- Жёсткие фильтры: география, категория, наличие на складе.

### 11.3 Approximate Nearest Neighbors (ANN)
- Проблема: точный поиск ближайших соседей в пространстве из сотен измерений — сложность `O(N)` на запрос, что слишком медленно при миллионах товаров.
- **LSH (Locality Sensitive Hashing):** хэшируем векторы так, что близкие в исходном пространстве попадают в одну хэш-корзину.
- **HNSW (Hierarchical Navigable Small World):** граф, где узлы — векторы, рёбра ведут к ближайшим соседям; поиск — жадный обход графа от «грубого» верхнего слоя к «точному» нижнему.
- **IVF (Inverted File Index):** предварительно кластеризуем все векторы, а на запрос ищем только внутри ближайших к запросу кластеров, а не по всей базе.
- **FAISS (Facebook AI Similarity Search)** — библиотека, реализующая эти индексы на CPU/GPU:
  - `IndexFlatIP` — точный полный перебор (используется как эталон для сравнения качества).
  - `IndexIVFFlat` — быстрый приближённый поиск на основе IVF.
  - `IndexHNSWFlat` — графовый индекс, один из самых быстрых на практике.

### 11.4 Stage 2: Ranking (точное ранжирование)
- Вход: ~1000 кандидатов, отобранных на предыдущей стадии, вместе с признаками.
- Модель: LightGBM / XGBoost / нейросеть (сюда напрямую переносится всё из Модуля 9 — Learning to Rank).
- Признаки:
  - Пользователь: возраст, история, средний чек.
  - Товар: цена, категория, средний рейтинг.
  - Контекст: время суток, устройство, геолокация.
  - Взаимодействие: сколько раз пользователь видел товар, кликал, добавлял в корзину.
- Выход: числовой score релевантности для каждого кандидата, по которому строится финальный порядок.

### 11.5 Stage 3: Re-ranking (бизнес-правила)
- **Дедупликация:** не показывать один и тот же товар дважды.
- **Blacklist:** исключить запрещённые/неприемлемые категории.
- **Diversity:** не показывать 5 телефонов подряд — перемешать категории (связь с Модулем 8.7).
- **Промо-вставки:** место для продвигаемых товаров/партнёрских предложений по бизнес-правилам, а не по модели.

### 11.6 Практика
- Построить минимальную двухстадийную систему: ALS/эмбеддинги → FAISS (Retrieval) → LightGBM (Ranking).
- Замерить и сравнить latency каждой стадии отдельно (Retrieval vs Ranking) — понять, где основной бюджет времени.

## Модуль 12. Проблемы в production и их решения

### 12.1 Холодный старт
- Новый пользователь: рекомендуем популярное + собираем сигнал через onboarding-вопросы («выберите интересные категории»).
- Новый товар: используем контентные фичи (Модуль 6) + временный «буст» новинок в выдаче для сбора первых сигналов.
- Гибридные подходы (Модуль 7) как основной инструмент решения обеих проблем.

### 12.2 Popularity Bias
- Проблема: модель стабильно рекомендует один и тот же топ-10, игнорируя длинный хвост каталога.
- Причина: по популярным товарам накоплено больше данных, поэтому модель увереннее в предсказаниях именно для них — это самоусиливающийся эффект.
- Решения: re-ranking с учётом Diversity (Модуль 11.5), exploration через ε-greedy (намеренное подмешивание менее очевидных вариантов), inverse propensity scoring (перевзвешивание обучающих примеров с учётом вероятности их показа).

### 12.3 Serendipity и Diversity
- Serendipity — приятная неожиданность (рекомендация релевантна, но не банальна).
- Diversity — разнообразие внутри одного списка рекомендаций.
- Обе величины измеряются метриками из Модуля 8.7 и улучшаются через re-ranking и explicit diversity-constraints в момент формирования финального списка.

### 12.4 A/B тестирование
- Почему офлайн-метрик (NDCG, Precision@K) недостаточно: они посчитаны на исторических данных, которые уже искажены поведением предыдущей модели (position bias, exposure bias) — высокий NDCG офлайн не гарантирует роста бизнес-метрик онлайн.
- Дизайн A/B теста для рекомендаций: разделение пользователей на группы, контроль за длительностью эксперимента (эффект новизны), выбор основной метрики заранее.
- Ключевые онлайн-метрики: CTR, конверсия, среднее время сессии, retention.

### 12.5 Онлайн vs Офлайн рекомендации
- **Офлайн:** модель обучена заранее, предсказания для всех пользователей посчитаны и закешированы (быстро отдавать, но менее актуально).
- **Онлайн:** предсказания считаются в реальном времени на основе самых свежих действий пользователя (точнее отражает текущий контекст, но требует инфраструктуры с низкой latency).
- **Гибрид:** базовый набор рекомендаций кэширован офлайн, но дополняется/переранжируется онлайн с учётом самых последних действий — практический компромисс, используемый большинством крупных систем.

### 12.6 Практика
- Реализовать стратегию холодного старта (переключение popularity → персонализированная модель по числу накопленных взаимодействий пользователя, как в Switching Hybrid из Модуля 7).
- Добавить diversity-constraint в финальный список рекомендаций (например, не более 2 товаров одной категории в топ-10) и посчитать, как это меняет Diversity и NDCG.

### 13.4 Retrieval stage: ALS + FAISS (`src/retrieval/train_als.py`)

```python
import implicit
import scipy.sparse as sp
import numpy as np
import faiss

# 1. Построение разреженной user-item матрицы (implicit feedback: rating >= 4 -> 1)
interactions = sp.csr_matrix((confidence, (user_idx, item_idx)))

# 2. Обучение ALS (Модуль 5.5)
model = implicit.als.AlternatingLeastSquares(
    factors=64, regularization=0.05, iterations=20
)
model.fit(interactions)

user_factors = model.user_factors   # shape: (n_users, 64)
item_factors = model.item_factors   # shape: (n_items, 64)

# 3. Построение FAISS индекса по эмбеддингам товаров (Модуль 11.3)
index = faiss.IndexHNSWFlat(item_factors.shape[1], 32)
index.add(np.ascontiguousarray(item_factors, dtype='float32'))
faiss.write_index(index, "models/item_index.faiss")

def get_candidates(user_id: int, k: int = 200) -> list[int]:
    """Retrieval: топ-K кандидатов через ANN-поиск в FAISS."""
    query = np.ascontiguousarray(
        user_factors[user_id].reshape(1, -1), dtype='float32'
    )
    distances, item_ids = index.search(query, k)
    return item_ids[0].tolist()
```

### 13.5 Ranking stage: LightGBM lambdarank (`src/ranking/train_ranker.py`)

```python
import lightgbm as lgb
import pandas as pd

# Обучающий датасет: строка = (user_id, item_id, признаки, релевантность 0/1)
# group — сколько строк-кандидатов относится к одному пользователю (Модуль 9.5)
groups = df.groupby('user_id').size().values

feature_cols = [
    'als_score',            # скалярное произведение user_factors и item_factors
    'popularity',
    'genre_match',          # пересечение жанров с историей пользователя (Модуль 6)
    'user_avg_rating',
    'hours_since_last_seen'
]

train_set = lgb.Dataset(
    df[feature_cols], label=df['relevance'], group=groups
)

params = {
    'objective': 'lambdarank',
    'metric': 'ndcg',
    'ndcg_eval_at': [10],
    'learning_rate': 0.05,
    'num_leaves': 31
}

ranker = lgb.train(params, train_set, num_boost_round=200)
ranker.save_model("models/ranker.txt")
```

### 13.8 Что говорить на собеседовании
> «Я построил двухстадийную рекомендательную систему: Retrieval через ALS-эмбеддинги и FAISS (HNSW-индекс) быстро отбирает 200 кандидатов из полного каталога, а LightGBM с `objective=lambdarank` точно ранжирует их в финальный топ-10, используя признаки пользователя, товара и контекста. Такое разделение — это прямое следствие constraint на latency: точную модель нельзя прогнать по всему каталогу, поэтому тяжёлая часть вычислений идёт только на уже отфильтрованных кандидатах. Оценивал качество через NDCG@10 и Precision@10 на temporal split, чтобы избежать утечки данных из будущего в прошлое.»

### 13.9 Типичные вопросы и ответы

| Вопрос | Ответ |
|:---|:---|
| «Почему ALS, а не сразу нейросеть?» | «ALS даёт быстрый, интерпретируемый и хорошо распараллеливаемый бейзлайн для эмбеддингов. Two-Tower модель — следующий логичный шаг, если потребуется учитывать больше контекстных признаков напрямую в эмбеддингах.» |
| «Почему LightGBM lambdarank, а не обычная классификация?» | «Задача — не предсказать факт клика по каждому товару отдельно (pointwise), а правильно упорядочить список. lambdarank напрямую оптимизирует NDCG, что ближе к бизнес-цели.» |
| «Как вы боретесь с popularity bias?» | «В признаки ranking-модели явно включена popularity, что позволяет модели учиться отделять "популярно, потому что релевантно" от "популярно само по себе", плюс на re-ranking накладывается ограничение по diversity категорий.» |
| «Почему temporal split, а не случайный?» | «Случайный сплит допускает, что в train попадёт взаимодействие из будущего относительно теста — модель неявно "подглядывает" и офлайн-метрики будут завышены относительно реального поведения в production.» |
| «Что будете делать с холодным пользователем?» | «Fallback на popularity-based рекомендации до накопления минимального числа взаимодействий, дальше — постепенный переход на персонализированную модель (Switching Hybrid, Модуль 7).» |
