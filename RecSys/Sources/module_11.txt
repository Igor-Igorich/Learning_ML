**Цель модуля:** формализовать production-архитектуру, которая уже была фактически описана по частям в предыдущих модулях — Cascade-гибрид (Модуль 7.2.5), Two-Tower модели (Модуль 10.3.3) и архитектура YouTube (Модуль 10.4) — и связать их в единый, законченный промышленный стандарт, лежащий в основе практически любой реальной рекомендательной системы с большим каталогом.

## 11.1 Почему одна модель не справляется

### 11.1.1 Формальный расчёт бюджета времени (latency budget)

Мы уже несколько раз в курсе апеллировали к интуитивному аргументу «нельзя прогнать тяжёлую модель по всему каталогу» (Модуль 10.3.3). Формализуем его точным расчётом.

Пусть каталог содержит `N=10 000 000` товаров, бюджет ответа на запрос — `50 мс`, и один forward pass ranking-модели (например, полноценной MLP из Модуля 10.1, а не просто скалярного произведения) для одной пары (пользователь, товар) занимает `0.5 мс` (реалистичная оценка для среднего по сложности нейросетевого инференса на CPU без батчинга).

```
Время на полный перебор каталога = N × время_на_1_товар = 10 000 000 × 0.5 мс = 5 000 000 мс = 5 000 секунд ≈ 83 минуты
```

**83 минуты вместо 50 миллисекунд** — расхождение в **~100 000 раз**. Это не «немного медленнее» — это принципиальная архитектурная невозможность, требующая не оптимизации существующего подхода, а **смены самой архитектуры**.

### 11.1.2 Решение — каскад стадий с убывающей скоростью и растущей точностью

```
10 000 000 товаров ──[Retrieval, быстро]──> ~200-1000 кандидатов ──[Ranking, точно]──> ~10-20 отранжированных ──[Re-ranking, бизнес-правила]──> финальный топ-10
```

Каждая следующая стадия работает с **на порядки меньшим** числом объектов, что позволяет применять на ней всё более тяжёлые и точные модели, не выходя за пределы latency budget. Это прямая реализация принципа Cascade из Модуля 7.2.5, но теперь с тремя стадиями вместо двух, и с явным акцентом на то, **какая именно метрика** важна на каждой стадии (раздел 11.1.3).

### 11.1.3 Разные метрики важны на разных стадиях — прямая связь с Модулем 8

| Стадия | Приоритетная метрика (Модуль 8) | Почему |
|:---|:---|:---|
| Retrieval | **Recall** (8.2) | Нельзя потерять релевантный товар на этом этапе — дальше его уже негде «найти» |
| Ranking | **NDCG, Precision@K** (8.5, 8.2) | Точный порядок в топ-10, который реально увидит пользователь |
| Re-ranking | **Diversity, Coverage** (8.7) | Качество списка **как целого**, а не отдельных позиций |

## 11.2 Stage 1: Retrieval (отбор кандидатов)

### 11.2.1 Множественные источники кандидатов

На практике Retrieval редко полагается на один источник сигнала — обычно объединяют несколько параллельных источников, каждый из которых использует уже знакомый вам алгоритм:

| Источник | Алгоритм из курса | Модуль |
|:---|:---|:---:|
| Коллаборативные «похожие товары» | Item-Based CF с предвычисленным top-k кэшем | 4.4 |
| Векторное сходство эмбеддингов | ALS / Two-Tower + ANN-поиск (раздел 11.3) | 5, 10.3 |
| Популярное/трендовое | Простой ранжированный список по популярности | 1.5.3, 12.1 (далее) |
| Контентное сходство | TF-IDF cosine similarity | 6 |
| Жёсткие фильтры | География, наличие на складе, возрастные ограничения | — |

**Дедупликация:** одни и те же товары нередко попадают в кандидаты сразу от нескольких источников (например, товар одновременно похож коллаборативно **и** контентно) — на выходе из Retrieval-стадии список кандидатов объединяется через операцию union с удалением дублей, часто с сохранением информации о том, **из какого источника** пришёл каждый кандидат (это становится полезным признаком для следующей стадии — Ranking, раздел 11.4).

### 11.2.2 Почему именно Recall, а не Precision, здесь приоритетен

Если Retrieval пропустит действительно релевантный товар (низкий Recall), Ranking-модель **никогда** не получит шанс его оценить — ошибка невосстановима на последующих стадиях. Если же Retrieval включит в список несколько нерелевантных кандидатов (низкая Precision на этом этапе) — это не страшно, потому что следующая, более точная стадия (Ranking) их просто отсеет. Асимметрия последствий ошибок разных типов — прямое обоснование того, почему на этой стадии сознательно жертвуют точностью ради полноты.

## 11.3 Approximate Nearest Neighbors (ANN)

### 11.3.1 Постановка задачи

Нужно быстро найти `k` товаров, эмбеддинги которых ближе всего к эмбеддингу запроса (пользователя), среди миллионов предвычисленных векторов (Модуль 10.3.3). Точный перебор — `O(N)` на запрос, что при больших `N` слишком медленно (тот же аргумент, что в 11.1.1). ANN-алгоритмы находят **приближённо** ближайших соседей значительно быстрее, жертвуя небольшой долей точности.

### 11.3.2 LSH (Locality Sensitive Hashing) — полный проверенный численный пример

**Идея:** хэш-функция специально сконструирована так, чтобы **близкие** в исходном пространстве векторы попадали в **одну** хэш-корзину с высокой вероятностью, а далёкие — в разные. Простейшая реализация — **случайная гиперплоскость**: генерируем случайный вектор `r`, и хэш-бит `h(v) = 1`, если `v·r ≥ 0`, иначе `0`. Несколько таких бит (от разных случайных `r`) объединяются в единый хэш-код.

**Проверка на векторах из Модуля 6.3.3** (4 случайные гиперплоскости, `seed=11`):
```
hash(I1) = 1001
hash(I2) = 0111
hash(I3) = 0110
hash(I4) = 1001   <-- ИДЕНТИЧЕН hash(I1)!
hash(I5) = 0001
```

**Хэш-корзины:**
```
1001: [I1, I4]
0111: [I2]
0110: [I3]
0001: [I5]
```

**Это не случайность, а прямое следствие того, что I1 и I4 — идентичные векторы** (Модуль 6.3.3: напомним, мы намеренно присвоили им одинаковые жанры, потому что они получали идентичные оценки во всех предыдущих модулях). Для **любой** случайной гиперплоскости `v·r` даёт одинаковый знак для двух идентичных векторов — поэтому вероятность совпадения хэша для идентичных (или очень близких) векторов **гарантированно высока**, а для непохожих — низка. В момент запроса нужно посчитать хэш **только** запроса и сравнить лишь с кандидатами из той же (или соседних) корзины — не со всей базой.

### 11.3.3 HNSW (Hierarchical Navigable Small World) — концептуальный разбор

**Идея:** построить граф, где узлы — векторы, а рёбра ведут к «навигационно близким» соседям, организованный в несколько **иерархических слоёв** — верхний слой содержит немного узлов с «дальнобойными» связями (для быстрого грубого перемещения по всему пространству), нижний слой содержит все узлы с «короткими» локальными связями (для точного финального поиска).

**Поиск (жадный обход):**
1. Начинаем с фиксированной точки входа на самом верхнем (разреженном) слое.
2. На каждом слое жадно двигаемся к соседу, наиболее близкому к запросу, пока не окажемся в локальном минимуме этого слоя.
3. Переходим на слой ниже, продолжаем жадный поиск с этой позиции — уже среди более плотных связей.
4. Повторяем до нижнего (самого плотного) слоя — финальный результат.

Аналогия для интуиции: верхний слой — это как перелёт на самолёте между городами (быстро преодолеваем большие расстояния), нижний слой — как пешая прогулка по конкретному кварталу (медленно, но точно находим нужный дом). `HNSW` в среднем даёт сложность поиска `O(log N)` вместо `O(N)` — асимптотика, знакомая вам по бинарному поиску и сбалансированным деревьям (Неделя 4 общего плана, BST), только здесь она достигается не через отсортированный порядок, а через специально построенную графовую навигационную структуру.

### 11.3.4 IVF (Inverted File Index) — полный проверенный численный пример

**Идея:** предварительно кластеризуем все векторы (например, через `KMeans`, уже знакомый вам алгоритм), а в момент запроса сравниваем его только с векторами из **ближайшего** (или нескольких ближайших) кластера, а не со всей базой.

**Проверка на векторах Модуля 6.3.3, `KMeans(n_clusters=2)`:**
```
Кластер 0: I1, I2, I3, I4
Кластер 1: I5

Запрос [0.5, 0.9, 0, 0, 0] (похож на I1/I4, Action+SciFi) -> назначен в кластер 0
IVF ищет только среди [I1, I2, I3, I4] -- пропуская I5 полностью
Экономия сравнений на этом крошечном примере: 20%
```

**Честное методологическое замечание:** на нашем игрушечном каталоге из 5 товаров экономия скромная (20%) — сам механизм, однако, масштабируется линейно с размером каталога. На реалистичном каталоге в `10 000 000` товаров с, скажем, `1000` кластеров, запрос в среднем сравнивается лишь с `~10 000` товарами вместо `10 000 000` — экономия **99.9%**, что снова возвращает время поиска в границы latency budget из раздела 11.1.1.

### 11.3.5 FAISS — библиотека, реализующая эти индексы

```python
import faiss
import numpy as np

item_embeddings = np.random.rand(1_000_000, 64).astype('float32')  # из ALS/Two-Tower, Модули 5/10

# Точный перебор (эталон для оценки качества приближения)
index_flat = faiss.IndexFlatIP(64)
index_flat.add(item_embeddings)

# IVF -- быстрый приближённый поиск (раздел 11.3.4)
quantizer = faiss.IndexFlatIP(64)
index_ivf = faiss.IndexIVFFlat(quantizer, 64, 100)  # 100 кластеров
index_ivf.train(item_embeddings)
index_ivf.add(item_embeddings)
index_ivf.nprobe = 10  # искать в 10 ближайших кластерах, не в 1 (компромисс скорость/точность)

# HNSW -- графовый индекс (раздел 11.3.3), обычно самый быстрый на практике
index_hnsw = faiss.IndexHNSWFlat(64, 32)  # 32 - число связей на узел
index_hnsw.add(item_embeddings)

query = np.random.rand(1, 64).astype('float32')
distances, candidate_ids = index_hnsw.search(query, k=200)  # top-200 кандидатов для Ranking-стадии
```

## 11.5 Stage 3: Re-ranking (бизнес-правила)

### 11.5.1 Дедупликация и Blacklist

Механические, не требующие сложной математики шаги: убрать повторы (если один товар каким-то образом просочился дважды), исключить категории по юридическим/этическим ограничениям.

### 11.5.2 Diversity через MMR (Maximal Marginal Relevance) — формула и полный проверенный численный пример

**Проблема:** Ranking-модель (11.4) оптимизирует релевантность **каждой позиции независимо** — она не «знает», что топ-2 и топ-3 в списке одинаковы по содержанию (прямая связь с Модулем 8.7.2, где мы уже увидели список `[I1,I4,I3]` с низкой Diversity, несмотря на высокую релевантность каждого элемента по отдельности).

**Формула MMR** (Carbonell & Goldstein, 1998) — жадный алгоритм, выбирающий на каждом шаге элемент, максимизирующий **компромисс** между релевантностью и непохожестью на уже выбранное:
```
MMR = argmax_{d_i ∈ R \ S} [ λ × Relevance(d_i) - (1-λ) × max_{d_j ∈ S} Sim(d_i, d_j) ]
```
где `R` — оставшиеся кандидаты, `S` — уже выбранный (финальный) список, `λ` — компромисс между релевантностью и разнообразием (`λ=1` — чистое ранжирование по релевантности, `λ=0` — максимальное разнообразие в ущерб релевантности).

**Полный проверенный численный пример.** Кандидаты после Ranking-стадии (11.4) с их релевантностью (гипотетические выходы LightGBM-ранкера) и уже знакомыми TF-IDF векторами (Модуль 6.3.3):
```
I1: relevance=0.90    I4: relevance=0.85 (идентичен I1!)    I3: relevance=0.70
I2: relevance=0.60    I5: relevance=0.50
```

**Наивный top-3 (просто по релевантности, без переранжирования):** `[I1, I4, I3]`

**MMR-переранжирование (`λ=0.7`), пошагово:**

*Шаг 1:* `I1` выбирается первым (максимальная чистая релевантность, штрафа за схожесть пока нет — список пуст).

*Шаг 2 — подробный расчёт для каждого оставшегося кандидата (после того как `I1` уже в списке):*
```
I4: MMR = 0.7×0.85 - 0.3×sim(I4,I1) = 0.5950 - 0.3×1.0000 = 0.5950 - 0.3000 = 0.2950
I3: MMR = 0.7×0.70 - 0.3×sim(I3,I1) = 0.4900 - 0.3×0.2371 = 0.4900 - 0.0711 = 0.4189
I2: MMR = 0.7×0.60 - 0.3×sim(I2,I1) = 0.4200 - 0.3×0.0000 = 0.4200 - 0.0000 = 0.4200
I5: MMR = 0.7×0.50 - 0.3×sim(I5,I1) = 0.3500 - 0.3×0.0000 = 0.3500 - 0.0000 = 0.3500
```

**Победитель шага 2: `I2` (MMR=0.4200)`, а не `I4`** — несмотря на то, что `I4` имеет значительно более высокую «сырую» релевантность (0.85 против 0.60), его MMR-score **ниже**, потому что штраф за практически полное совпадение с уже выбранным `I1` (`sim=1.0000`) перевешивает выигрыш в релевантности.

*Шаг 3 (после `{I1, I2}`):* аналогичный расчёт выбирает `I3` (детали опущены для краткости, механика идентична шагу 2).

**Итоговый MMR top-3: `[I1, I2, I3]`** — против наивного `[I1, I4, I3]`.

### 11.5.3 Интерпретация — почему это лучший бизнес-результат

MMR **осознанно пожертвовал** позицией с более высокой «сырой» релевантностью (`I4`, 0.85) ради позиции, добавляющей реальную новую информацию списку (`I2`, 0.60, но совершенно другого жанра). Пользователю показывают не «`I1` плюс почти его копию», а три содержательно разных варианта — прямая практическая реализация принципа Diversity (Модуль 8.7.2), встроенная в конвейер как явный, интерпретируемый, математически обоснованный алгоритм, а не как случайное следствие работы Ranking-модели.

## 11.6 Практика

### 11.6.1 Полный конвейер, связывающий все модули курса воедино

```python
def full_recommendation_pipeline(user_id: int, k_final: int = 10):
    # === Stage 1: Retrieval (разделы 11.2-11.3) ===
    ann_candidates = ann_index.search(user_embeddings[user_id], k=200)       # Модули 5, 10, 11.3
    cf_candidates = item_based_cf_cache.get_similar(user_history[user_id])   # Модуль 4.4
    popular_candidates = popularity_fallback.get_top(k=50)                   # Модуль 12 (далее)
    candidates = deduplicate(ann_candidates + cf_candidates + popular_candidates)  # 11.2.1

    # === Stage 2: Ranking (раздел 11.4, Модуль 9) ===
    features = build_ranking_features(user_id, candidates)  # Таблица 11.4.1
    scores = ranker.predict(features)                       # LightGBM lambdarank
    ranked_candidates = sorted(zip(candidates, scores), key=lambda x: -x[1])[:50]

    # === Stage 3: Re-ranking (раздел 11.5) ===
    final_list = mmr_rerank(ranked_candidates, item_vectors, k=k_final, lam=0.7)
    final_list = apply_business_rules(final_list)  # dedup, blacklist (11.5.1)

    return final_list
```

## Глоссарий модуля 11

| Термин | Короткое определение |
|:---|:---|
| Latency budget | Максимально допустимое время ответа системы на один запрос |
| Retrieval (Candidate Generation) | Быстрая стадия отбора кандидатов из полного каталога |
| ANN (Approximate Nearest Neighbors) | Приближённый (не точный) поиск ближайших векторов |
| LSH | ANN-метод через хэширование случайными гиперплоскостями |
| HNSW | ANN-метод через иерархический навигационный граф |
| IVF | ANN-метод через предварительную кластеризацию векторного пространства |
| Ranking | Точная стадия ранжирования ограниченного числа кандидатов |
| Re-ranking | Финальная корректировка списка бизнес-правилами (dedup, diversity) |
| MMR (Maximal Marginal Relevance) | Жадный алгоритм переранжирования, балансирующий релевантность и разнообразие |

---

**Связь со следующим модулем:** архитектура этого модуля предполагает, что все её компоненты (ALS-эмбеддинги, item-item сходство, Ranking-модель) уже **обучены на достаточном объёме данных**. Модуль 12 разбирает, что происходит, когда это предположение нарушается — холодный старт, systematic bias, необходимость A/B-тестирования — то есть все те практические сложности, которые проявляются уже после того, как система из этого модуля развёрнута в production.
