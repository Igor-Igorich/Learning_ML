# Конспект. Модуль 9: Learning to Rank — ML, который учится ранжировать

**Курс:** Мини-курс RecSys (13 модулей)
**Модуль:** 9 из 13 — «Learning to Rank: ML, который учится ранжировать»
**Цель модуля:** сделать логичный следующий шаг после Модуля 8 — если мы теперь умеем **измерять** качество ранжирования (Precision@K, NDCG и т.д.), возникает естественный вопрос: а можно ли **обучать модель напрямую оптимизировать именно эти метрики**, а не косвенные прокси вроде RMSE (Модуль 5)? Это и есть область Learning to Rank (LTR).

**Связь с предыдущими модулями:** формально, Funk SVD и ALS (Модуль 5) — это уже пример **pointwise** LTR, просто без явного использования этого термина: они минимизируют поточечную ошибку `(r_ui - pred)²`. BPR (Модуль 5.6) — уже пример **pairwise** LTR. Этот модуль не вводит принципиально новую математику с нуля, а **систематизирует** то, что вы частично уже видели, вводит недостающее звено (listwise), и явно формулирует, чем эти три класса подходов различаются — это системообразующий модуль для понимания архитектуры Ranking-стадии в Модуле 11.

---

## 9.1 Постановка задачи

### 9.1.1 Формальная переформулировка

Вход: тройки `(пользователь, товар, признаки)`. Выход: числовой score релевантности, по которому строится итоговый порядок. Признаки здесь — это уже не просто «ID пользователя» и «ID товара» (как в чистой матричной факторизации, Модуль 5), а полноценный вектор признаков — прямая связь с тем самым feature engineering, который вы уже отрабатывали в проекте FraudGuard (пользовательские агрегаты, признаки товара, контекстные признаки — полный список появится в Модуле 11.4).

### 9.1.2 Ключевое структурное понятие — «группа» (group)

В отличие от обычной задачи регрессии/классификации, где каждая строка обучающей выборки независима, в LTR строки **группируются** по пользователю (или, в терминологии информационного поиска, по «запросу», отсюда часто встречающееся название `query_id`/`group_id` в библиотеках). Все метрики Модуля 8 (Precision@K, NDCG и т.д.) считаются **внутри одной группы** — они сравнивают товары **относительно друг друга** для данного конкретного пользователя, а не в среднем по всему датасету. Это структурное отличие — то, что необходимо явно передавать в LightGBM через параметр `group` (раздел 9.5) — без корректно заданных групп модель не будет знать, какие строки сравнивать друг с другом при вычислении ranking-ориентированной функции потерь.

### 9.1.3 Три класса методов — обзорная карта

| Подход | Что оптимизируется | Пример из уже пройденного |
|:---|:---|:---|
| **Pointwise** | Абсолютное значение релевантности для каждого товара независимо | Funk SVD, ALS (Модуль 5) |
| **Pairwise** | Относительный порядок внутри **пар** товаров | BPR (Модуль 5.6) |
| **Listwise** | Метрика качества **всего списка** целиком | LambdaMART |

## 9.2 Pointwise подход

### 9.2.1 Формулировка

Каждый товар оценивается **независимо** от остальных — задача сводится к обычной регрессии (предсказать точный рейтинг/score) или классификации (предсказать вероятность клика). Модели: логистическая регрессия, MSE-регрессия, градиентный бустинг с обычным `objective='regression'` или `'binary'`.

### 9.2.2 Ключевая проблема — несогласованность с целевой ranking-метрикой

Pointwise-функция потерь (например, MSE) **не знает** о существовании понятия «порядок» — она штрафует за отклонение от истинного значения **отдельно** для каждого товара, суммируя эти штрафы без учёта того, как они соотносятся друг с другом внутри списка одного пользователя. Из этого следует контринтуитивный, но важный факт: **модель с более низким MSE может давать худшее ранжирование**, чем модель с более высоким MSE.

### 9.2.3 Полный проверенный численный пример несогласованности

Пользователь оценивает два товара, истинная релевантность: `rel(A)=3, rel(B)=1` (A объективно предпочтительнее B).

**Модель 1** предсказывает `[A=1.5, B=0.5]` — абсолютные значения далеки от истины, но **относительный порядок верен** (A>B):
```
MSE₁ = ((3-1.5)² + (1-0.5)²) / 2 = (2.25 + 0.25) / 2 = 1.250

Ранжирование по предсказанию: [A, B] — совпадает с истинным порядком
NDCG₁ = 1.0000  (идеальное ранжирование)
```

**Модель 2** предсказывает `[A=1.9, B=2.0]` — абсолютные значения **ближе** к истинным средним (интуитивно «лучше откалибрована»), но относительный порядок **неверный** (модель считает B>A):
```
MSE₂ = ((3-1.9)² + (1-2.0)²) / 2 = (1.21 + 1.00) / 2 = 1.105

Ранжирование по предсказанию: [B, A] — НЕ совпадает с истинным порядком
DCG₂ = rel(B)/log2(2) + rel(A)/log2(3) = 1/1.000 + 3/1.585 = 1.000 + 1.893 = 2.893
IDCG = rel(A)/log2(2) + rel(B)/log2(3) = 3/1.000 + 1/1.585 = 3.000 + 0.631 = 3.631
NDCG₂ = 2.893 / 3.631 = 0.7967
```

**Итог, критически важный для понимания всего модуля:**
```
MSE₂ (1.105) < MSE₁ (1.250)   — Модель 2 «лучше» по pointwise-метрике
NDCG₂ (0.797) < NDCG₁ (1.000) — но Модель 2 ХУЖЕ по ranking-метрике
```

Модель 2 формально минимизирует pointwise-функцию потерь эффективнее, но при этом **портит порядок**, который реально важен для бизнеса (Модуль 1.3.3 — напомним, порядок в top-K важнее точных абсолютных значений). Это не искусственный, надуманный пример — это структурное, систематическое ограничение всего класса pointwise-методов, и именно оно мотивирует переход к pairwise и listwise подходам.

## 9.3 Pairwise подход

### 9.3.1 Общая идея

Вместо «предскажи правильное число для каждого товара», pairwise-подход прямо спрашивает: «для пары товаров `(i, j)`, какой из них должен стоять выше?» — и оптимизирует именно эту, более простую и напрямую релевантную для ранжирования, задачу.

### 9.3.2 RankNet — общая формулировка через кросс-энтропию

Для пары `(i, j)` определяется:
- **Целевая вероятность** `S_ij`: `1`, если `i` истинно более релевантен, чем `j`; `0`, если наоборот; `0.5`, если релевантности равны (ничья).
- **Предсказанная вероятность** того, что `i` более релевантен, чем `j`:
```
P_ij = σ(s_i - s_j)
```
где `s_i, s_j` — сырые скоры модели, `σ` — сигмоида.

**Функция потерь — бинарная кросс-энтропия** (та же самая конструкция, что вы уже видели в LogLoss логистической регрессии, Неделя 4 общего плана — только применённая не к абсолютному классу объекта, а к **относительному сравнению пары**):
```
L_ij = -S_ij·ln(P_ij) - (1-S_ij)·ln(1-P_ij)
```

### 9.3.3 Полный проверенный численный пример — RankNet loss для «ошибочной» Модели 2

Используем Модель 2 из раздела 9.2.3 (`s_A=1.9, s_B=2.0`, при этом истинно `rel(A)=3 > rel(B)=1`, значит `S_AB=1`):
```
s_A - s_B = 1.9 - 2.0 = -0.1000

P_AB = σ(-0.1000) = 0.4750

L_AB = -1.0×ln(0.4750) - 0×ln(1-0.4750) = -ln(0.4750) = 0.7444
```

**Интерпретация:** модель предсказывает, что вероятность `A > B` составляет лишь `47.5%` — то есть модель практически «не уверена» и склоняется к неверному ответу (раз `P_AB < 0.5`, это означает `P_ij` для «B выше A» больше 50%, что и есть ошибка). Функция потерь `0.744` явно штрафует за это — в отличие от MSE (раздел 9.2.3), которая в этом же примере, наоборот, «поощрила» Модель 2 более низким значением.

### 9.3.4 BPR как частный случай pairwise — явная связь с Модулем 5.6

BPR, разобранный в Модуле 5.6 для implicit-данных, — это **тот же самый** математический аппарат: `x_uij = p_u·q_i - p_u·q_j` — прямой аналог `s_i - s_j` из RankNet, только специализированный под задачу «взаимодействовал / не взаимодействовал» вместо общей градуальной релевантности. Если вы поняли вывод градиентов BPR (Модуль 5.6.3), вы уже, по сути, поняли и вывод градиентов RankNet — это один и тот же математический паттерн, применённый в двух разных постановках задачи.

### 9.3.5 Ограничение pairwise-подхода

Pairwise-методы оптимизируют **каждую пару** формально одинаково важной — то есть паре товаров на позициях 1 и 2 придаётся такой же вес в функции потерь, как и паре на позициях 99 и 100. Но для бизнеса ошибка на первых позициях (пользователь их реально видит) намного дороже ошибки в конце длинного списка. Это структурное ограничение мотивирует переход к listwise-подходу.

## 9.4 Listwise подход

### 9.4.1 LambdaMART — прямая оптимизация метрики целиком

**Идея:** вместо того чтобы независимо штрафовать каждую пару поровну (9.3.5), взвесить вклад каждой пары величиной **реального влияния этой пары на итоговую ranking-метрику** (обычно NDCG) — если перестановка конкретной пары товаров сильно меняет NDCG всего списка, её градиент должен быть больше; если почти не меняет — градиент должен быть меньше.

### 9.4.2 «Lambda» — псевдо-градиент

```
λ_ij = (стандартный RankNet-градиент для пары i,j) × |ΔNDCG_ij|
```
где `ΔNDCG_ij` — изменение NDCG всего списка, если поменять местами позиции `i` и `j`, оставив все остальные позиции без изменений. `λ` здесь называется «псевдо-градиентом», потому что NDCG как функция сама по себе не дифференцируема (это функция от **ранга**, дискретной, а не непрерывной величины) — LambdaMART обходит эту проблему, напрямую конструируя осмысленный градиент, минуя необходимость дифференцировать саму метрику.

### 9.4.3 Полный проверенный численный пример — почему разные перестановки получают разный вес

Рассмотрим список из трёх товаров `C, B, A` с истинными релевантностями `rel(C)=0, rel(B)=1, rel(A)=3`. Модель по ошибке выдала их в **полностью обратном** правильному порядке: `[C, B, A]` (позиция 1 → C, позиция 2 → B, позиция 3 → A):

```
Текущий DCG = rel(C)/log2(2) + rel(B)/log2(3) + rel(A)/log2(4)
            = 0/1.000 + 1/1.585 + 3/2.000
            = 0 + 0.631 + 1.500 = 2.131

IDCG (идеальный порядок A,B,C) = 3/log2(2) + 1/log2(3) + 0/log2(4) = 3.000+0.631+0 = 3.631

Текущий NDCG = 2.131 / 3.631 = 0.5869
```

**Сценарий swap №1 — поменять местами позиции 1 и 3 (C и A)**, новый порядок `[A, B, C]` (это и есть правильный, идеальный порядок!):
```
Новый DCG = 3/log2(2) + 1/log2(3) + 0/log2(4) = 3.000+0.631+0 = 3.631 = IDCG
Новый NDCG = 1.0000

ΔNDCG(1,3) = 1.0000 - 0.5869 = 0.4131
```

**Сценарий swap №2 — поменять местами позиции 1 и 2 (C и B)**, новый порядок `[B, C, A]`:
```
Новый DCG = 1/log2(2) + 0/log2(3) + 3/log2(4) = 1.000+0+1.500 = 2.500
Новый NDCG = 2.500 / 3.631 = 0.6885

ΔNDCG(1,2) = 0.6885 - 0.5869 = 0.1016
```

**Ключевой вывод:** `|ΔNDCG(1,3)| = 0.4131` значительно **больше**, чем `|ΔNDCG(1,2)| = 0.1016`. Это означает, что LambdaMART придаст **значительно больший вес** градиенту для пары `(C, A)` (позиции 1 и 3), чем для пары `(C, B)` (позиции 1 и 2) — потому что исправление первой ошибки («перепутали максимально релевантный товар с максимально нерелевантным, поставив их на противоположные полюса выдачи») даёт намного больший прирост итоговой бизнес-метрики, чем исправление второй. Это математически формализует интуитивно понятную вещь: LambdaMART «понимает», что не все ошибки ранжирования одинаково дороги, и явно фокусирует обучение на исправлении самых дорогих из них.

### 9.4.4 Почему LambdaMART — industry standard

Именно эта способность — напрямую оптимизировать реальную бизнес-метрику (NDCG), а не суррогатную pointwise/pairwise-прокси, при этом оставаясь совместимым с эффективными и хорошо изученными алгоритмами градиентного бустинга (тот же LightGBM, который вы изучаете в параллельном треке общего плана) — сделала LambdaMART стандартом де-факто в промышленных поисковых и рекомендательных системах (используется, в частности, в Yandex, Google, Amazon).

## 9.5 Практика

### 9.5.1 LightGBM с `objective='lambdarank'`

```python
import lightgbm as lgb
import numpy as np
import pandas as pd

# Обучающий датасет: каждая строка = (user_id, item_id, признаки, релевантность)
# Признаки - прямая связь с Модулем 11.4 (полный список признаков для Ranking stage)
train_df = pd.DataFrame({
    'user_id': [...],
    'item_id': [...],
    'als_score': [...],           # скор из Модуля 5.5 (Meta-level гибрид, Модуль 7.2.4!)
    'content_similarity': [...],  # косинус из Модуля 6
    'popularity': [...],
    'relevance': [...],           # 0/1 или градуальная релевантность (0-4)
})

# КРИТИЧЕСКИ ВАЖНО: строки должны быть отсортированы по группам (user_id) подряд
train_df = train_df.sort_values('user_id')

# group - сколько строк-кандидатов относится к каждому пользователю (раздел 9.1.2)
groups = train_df.groupby('user_id').size().values

feature_cols = ['als_score', 'content_similarity', 'popularity']

train_set = lgb.Dataset(
    train_df[feature_cols],
    label=train_df['relevance'],
    group=groups
)

params = {
    'objective': 'lambdarank',   # именно LambdaMART из раздела 9.4
    'metric': 'ndcg',
    'ndcg_eval_at': [5, 10],
    'learning_rate': 0.05,
    'num_leaves': 31,
}

ranker = lgb.train(params, train_set, num_boost_round=200)
```

### 9.5.2 Сравнение трёх подходов на одинаковых данных

- Обучить три модели на одном и том же датасете признаков (MovieLens + признаки из Модулей 5, 6):
  - **Pointwise:** `LGBMRegressor` с `objective='regression'` (предсказание релевантности напрямую).
  - **Pairwise:** `implicit.bpr.BayesianPersonalizedRanking` (уже знакомая модель из Модуля 5.7.2) или LightGBM с кастомной pairwise-целью.
  - **Listwise:** LightGBM с `objective='lambdarank'` (раздел 9.5.1).
- Для каждой модели посчитать NDCG@10 (Модуль 8.5) на одном и том же test-сете (temporal split, Модуль 1.7).
- **Ожидаемый и уже теоретически обоснованный результат** (разделы 9.2.3, 9.4.3-9.4.4): listwise (LambdaMART) обычно даёт наивысший NDCG, pointwise — наинизший, при том что MSE у pointwise-модели, скорее всего, будет **наилучшим** среди всех трёх (это и есть практическое воспроизведение несогласованности, продемонстрированной в 9.2.3, но уже на реальных данных, а не на игрушечном примере из двух товаров).

## Глоссарий модуля 9

| Термин | Короткое определение |
|:---|:---|
| Learning to Rank (LTR) | Обучение модели напрямую для задачи ранжирования, а не рейтинг-предсказания |
| Group / Query ID | Группировка строк обучающей выборки по пользователю/запросу |
| Pointwise | Независимая оценка релевантности каждого товара |
| Pairwise | Оптимизация относительного порядка внутри пар товаров |
| Listwise | Прямая оптимизация метрики качества всего списка |
| RankNet | Pairwise-метод через бинарную кросс-энтропию на предсказанной вероятности порядка |
| LambdaMART | Listwise-метод, взвешивающий pairwise-градиенты по реальному влиянию на NDCG |
| Lambda (λ) | Псевдо-градиент, учитывающий изменение метрики при перестановке пары |

---

**Связь со следующим модулем:** LightGBM с `lambdarank` (раздел 9.5) — мощный, но полностью **линейный по входным признакам** метод в том смысле, что признаки (`als_score`, `content_similarity` и т.д.) должны быть заданы заранее, вручную. Модуль 10 вводит следующий уровень абстракции — нейросетевые эмбеддинги, которые **сами обучаются** находить полезные представления пользователей и товаров прямо из сырых данных, не требуя ручного feature engineering для самой сути «похожести».
